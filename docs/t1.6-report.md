### 2.1 倍率语义（§A）

```
8d6>=4[>=5*2]  resArray=[1,2,3,5,6,6,1,1]  → 成功数:3, 追加カウント[>=5]：6
8d6>=4[>=5*2]  resArray=[5,1,2,3,4,2,1,3]  → 成功数:2, 追加カウント[>=5]：2   (1 命中 × 2)
8d6>=4[>=5]    resArray=[1,2,3,5,6,6,1,1]  → 成功数:3, 追加カウント[>=5]：3   (对照，无倍率)
```

**铁律：倍率 = 命中数 × N**（`dice.js:162` 逐个命中累加 `appSum += app[k].bairitsu`），不是「命中数 + N」也不是「取最大」。

### 2.2 异常倍率（§B，**四条全部实测**）

| 输入 | 天狗 `bairitsu` | 天狗行为 | 根因 |
|---|---|---|---|
| `8d6>=4[>=5*0]` | **0** | 照常响应，显示 0 | `Number("0")` = 0 |
| `8d6>=4[>=5*x]` | **1** | **照常响应**（降级为默认 1，不拒答） | `isNaN("x")` → true → 落 `? 1` 分支 |
| `8d6>=4[>=5*]` | **0** | 照常响应，显示 0 | `split` 出空串 → `Number("")` = **0**（不是 1！） |
| `8d6>=4[>=5*2.5]` | **2.5** | 照常响应，**出 .5 的小数** | `Number("2.5")` = 2.5，无取整 |

⚠ 天狗 `isNaN` 的边界实测（Node）：`isNaN("") === false`、`isNaN("=") === true`。
所以「裸 `*`」这条分支之所以给 0 而不是 1，靠的是 `Number('')` 而非 isNaN。

## 4. S 前缀保护泛化（预警 2 落实）

### 4.1 泛化前的问题

T1.5 的覆写把 `SEISEN` **硬编码**进保护分支：

```ruby
Regexp.new("\\A(?:SEISEN|#{super.source})", Regexp::IGNORECASE)
```

这是**打补丁形态**：每注册一个 S 开头的前缀都得记得再改这里，漏一个就复现同款阻塞 bug（T1.5 实测 `SEISEN9` 完全不响应，而 `eval_game_system_specific_command` 直调正常）。

**实测确认泛化确有价值**：本类 S 前缀实际有 3 个——`SEISEN`（T1.5 加）、`SBX`（T1.3 加）、`SB`（父类）。其中 `SBX` 与 `SB` 是**互为前缀**的关系，`SB|SBX` 的排列会因「先到先得」让 `SBX` 命中 `SB` 分支剩 `X`——正是原 bug 的形态。故排序必须**按长度降序**。

### 4.2 泛化实现

```ruby
def self.s_protected_prefixes
  # 首次调用即冻结（与上游 prefixes_pattern 同一时序铁律）
  @s_protected_prefixes ||= prefixes.grep(/\A[Ss]/).sort_by { |p| [-p.length, p] }.freeze
end

def self.prefixes_pattern
  @prefixes_pattern ||= Regexp.new(
    "\\A(?:#{s_protected_prefixes.join('|')}|#{super.source})",
    Regexp::IGNORECASE
  ).freeze
end
```

- **动态收集**：首次调用 `prefixes_pattern` 时从 `self.prefixes` 取。当时全部 `register_prefix` 已在类体内完成（时序铁律），冻结后列表**恒定封闭**。
- **长度降序**：保证最长前缀先试（`SEISEN|SBX|SB`）。
- **结构断言从硬编码改为通式**：`test/engine_structure_test.rb` 现在断言
  `"\\A(?:#{EX.s_protected_prefixes.join('|')}|#{ref.source})"`——
  **把泛化改回单前缀硬编码会当场红**。

### 4.3 回归用例（预警 2 要求的两个证明）

| 断言 | 位置 | 证明 |
|---|---|---|
| `test_s_protected_prefixes_is_dynamic_and_complete` | engine_structure_test | 集合 == 所有 S 前缀（漏一个即红）、长度降序、已冻结、含 SEISEN/SBX/SB |

## 5. 偏离与取舍（逐条申报）

### 5.1 `[C]` 不搬（计划 §5 拍板）

天狗 `[C]` = `=4/コッポ判定`（出目 4 数カウント）；BCDice 上游 `[C]` = クリティカル判定（`RE_COUNT_CRITICAL`）。**同名不同义 → 保上游**。

- 结构守卫钉死：`assert_not_include(APPENDIX_ONE_FRAGMENT, "[C]")`
- toml 双向钉死：`K6[C]` → `クリティカル判定[C]:2[6,6]`；`K6[=4]` → `追加判定[=4]:2[4,4]`（コッポ的替代写法）
- HELP_MESSAGE 已写明「コッポ判定には `[=4]` を使ってください」

### 5.2 合计値口径：倍率**不**并入成功数 ⚠️ 主要偏离

天狗 `dice.js:170` 的 `this.sum += appSum` 把倍率后的命中数**并入合计**。
BCDice 父类的追加判定**从不并入成功数**（`proc_dice_2nd` 只把 `roll_result.success_num` 累进 `total_success_num`）。

**本扩展选择**：沿用父类模型，倍率只放大追加カウント的**显示值**。

**理由**：父类的成功数是判定成败的输入。一旦并入倍率项，`K6[>=5*2]` 的成败就会随倍率改变——而天狗那边「成功数」与「追加カウント」是两个独立呈现的口径，合计值只是展示。用户要合计值时用 `calc` 自行相加。

**风险**：熟悉天狗的玩家可能期望「合计」含倍率项。当前输出把两口径分得很清楚（`成功数:5, 追加判定[>=5]:4`），不产生歧义。

### 5.3 `*非数字` 由「降级为 1」收紧为「不响应」

天狗 `[>=5*x]` 静默按倍率 1 输出。本扩展整条不响应。
**理由**：玩家打 `*x` 时几乎一定是把倍率写错了；静默按 1 输出会让他以为生效了。宁可拒答也不给假信息。

### 5.4 分隔符：只用 `][`，不收天狗的 `,`

天狗 `[J,L]` 与 `[J][L]` 完全等价（§2.4 实测）。BCDice 父类只用 `][`；引入第三种分隔符会让同一类命令出现两种多段写法。`K6[J,L]` 在本扩展不响应（异常系有用例钉住）。

### 5.5 默认标签用「追加判定」而非天狗的「追加カウント」

天狗 `Appendix.js:11` 的默认 comment 硬编码 `'追加カウント'`（日文不同）。
本扩展沿用父类 BCDice 的「追加判定」，理由：
1. 同一命令里 `K6[J][>=5*2]` 两段风格统一（记忆符标签是日文专名，普通段是 BCDice 术语）；
2. 与 `NinjaSlayer2.toml` 孪生对拍天然对齐——父类 `[>=5]` 输出的是「追加判定」，若本扩展写「追加カウント」会造成同一父类命令在子类里变样文。

故该常量 `APPENDIX_DEFAULT_LABEL` **不进 yml**（进 yml 会让人误以为能逐字回读天狗）。

### 5.6 倍率上界 `bairitsu_max = 100`（本扩展新增，天狗无上界）

天狗 `[>=5*999999]` 合法（`Appendix.js:19` 只判 isNaN）。本扩展对超界**整条不响应**，避免手滑长数字产出天文数字的伪计数。数值写在 yml（生成期常量），代码只读。`K6[>=5*100]` 正常响应（用例钉住边界）。

### 5.7 集合判定 `665+` 不与倍率组合

天狗 appendix 的 border 走 `Number(strArray[2])`，`665+` → NaN → `checkAppendix` 抛错，即**天狗根本不支持集合判定**。BCDice 父类支持（走 `super`，零改动）。本扩展的倍率形态**只收单值 `[1-6]`**——否则 `[>=665+*2]` 会在这里静默生效，与天狗相反。`K6[>=665+*2]` 不响应（异常系钉住）。

## 7. 实现期真实踩到的 bug（4 个，全部被自建守卫当场抓住）

### 7.1 正则交替优先级（本任务最隐蔽的一个）

初版片段写成 `((?:[<>!]?=)([1-6])\*(...)|([JL]))`——外层是**捕获组**。
正则交替的 `|` 优先级**低于**分组，于是这个 `|` 落在了捕获组**内部**：

```
m[1] = ">=5*2"   ← 不是 ">="，而是整条 appendix 原文
m[2] = "5"  m[3] = "2"  m[4] = nil
```

表现：`K6[J]` 能工作、`K6[>=5*2]` **静默不响应**（op 变成 `">=5*2"` → `comparison_operator` 返回 nil → 整条 nil）。
`engine_structure_test` 的「片段+锚点恒等式」断言当场把它照出来。

修正：外层改 `(?:…)`，并把判定符组写成与父类**逐字同源**的 `(=|!=|>=|>|<=|<)`（而不是 `[<>!]?=`——后者漏掉裸 `=`，会让 `[=6*2]` 失配）。

### 7.2 i18n 返回 Symbol 键

`fetch("border")` → `KeyError: key not found: "border"; Did you mean? :border`。
BCDice 的 `Translate` 把 YAML 载入后 symbolize。改为 `fetch(:border)`。

### 7.3 Integer / String 类型不一致

记忆符的 border 从 i18n 读出来是 `Integer(1)`，比较分支的 y 是 `String("6")`。
共用 `end_with?("+")` 时炸 `undefined method 'end_with?' for 1:Integer`。
统一 `to_s`（比较分支的 y 本来就是字符串，`to_s` 是 no-op）。

### 7.4 ⚠️ 先掷骰后校验（最有价值的一个）

初版 `proc_ex_diceroll` 是「掷骰 → 逐段校验 → 非法则 return nil」。
问题：`K6[>=5*101]` 会**先掷 6 颗骰再返回 nil**。对玩家无害（结果丢弃），但：
1. toml 异常系用例只能写空/1 颗 rands → runner 报 **Error**（`@rands is empty!`）而非 Assertion，掩盖了真正的问题；
2. 白掷骰是纯粹的资源浪费。

修正：拆成 **parse（不掷骰）/ count（要骰子）** 两层，先全量校验后掷骰。
「非法即不响应**且不掷骰**」从此是构造上的必然，而非靠调用顺序凑巧——
`test_invalid_appendix_rejected_before_rolling`（只喂 1 颗骰）把它钉住。

## 9. 遗留与建议

1. **`§5.2 合计口径`** 是本任务唯一有实质分歧的偏离。若后续用户要求「合计含倍率项」，
   需要改 `proc_ex_diceroll` 的 `total_success_num` 累加逻辑 + 一批 toml 期望值，
   届时建议先确认口径再动（会改变 `K6[>=5*2]` 的成功/失败标志）。
2. **`bairitsu_max = 100`** 是拍板级的安全上限，不是天狗数据。改它只需改
   `json_to_i18n.rb` 的生成值（代码只读 yml），无需改实现。
3. **`APPENDIX_DEFAULT_LABEL`「追加判定」** 若将来要跟天狗统一成「追加カウント」，
   会同时影响 NinjaSlayer2.toml 孪生对拍的期望（父类输出不变、子类变），
   届时需一并处理。
