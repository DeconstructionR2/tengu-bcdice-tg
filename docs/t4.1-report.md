## 2. 交付链路（计划 §9：源码 rsync → 生产机构建）

```
rsync -a --delete \
  --exclude='/.git/' --exclude='/.env' --exclude='/.bundle/' --exclude='/vendor/' \
  --exclude='/references/src/' --exclude='/data/' --exclude='/tmp/' \
  --exclude='*.db' --exclude='*.db-wal' --exclude='*.db-shm' --exclude='*.log' \
  ~/projects/tengu-bcdice-tg/ /opt/<project>/src/
cd /opt/<project>/src && sudo docker build --no-cache -t tengu-bcdice-tg:latest .
```

**实测坑（两次，均已修，留档防复发）**：`data/` 这类「裸名字模式」在 **rsync 与
.dockerignore 两侧都会匹配任意深度**——首次构建时 `test/data/`（toml 夹具）被
rsync 悄悄滤掉，构建闸门当场红（`No target found!`，exit 1）。这正是闸门存在
的意义：**坏上下文进不了镜像**。修法 = 两侧一律 `/` 锚定根目录模式；另用实验
（原地探针 ×6 变体）实测确认本机 legacy builder 对 `/data/`、`data`、`data/*`
的匹配行为，最终采用锚定写法（对 legacy 与 BuildKit 双语义均正确）。

构建上下文 = 工作树全量 - 上述排除清单（含 `test/`、`references/extracted/`
——构建期 verify 需要；`references/extracted/` 的 ledger/tables.json 是
ledger_consistency 测试的数据源）。

## 5. 冒烟记录（验收 #2）

### 5.1 前置安全分析（为什么冒烟不是「直接起一个容器」）

本机已有**开发态测试 bot 进程**（`/usr/bin/ruby … load "bot/main.rb"`，TENGU_ENV=test，
pid 不变、自 01:11 起运行）在用**同一个测试 token** 长轮询。Telegram 每 bot 只允许
一个 getUpdates 消费者：后到的请求会**终止**先到者的长轮询（409），而本仓库栈对
409 是**未捕获崩溃链**（gem `api.rb` 非 200 即 raise；`client.rb#fetch_updates` 只
rescue Timeout/ConnectionFailed；`main.rb` 对 `listen` 无兜底）——直接起冒烟容器
= 打死 dev bot（违反硬红线「不要 kill/重启它」）。

**冒烟时序（两次执行均照此）**：SIGSTOP dev bot（冻结，非 kill）→ 等 35s 让在途
长轮询（gem `timeout=20`）在服务端自然到期（此后 Telegram 侧消费者数 = 0）→ 起
冒烟容器独占轮询 → 验证 → 删容器 → 确认无消费者 → SIGCONT（dev bot 读掉缓冲
空响应、立即重新轮询）。全程零并发窗口；脚本 trap 兜底（任何失败先删容器再 CONT）。

### 5.2 启动序列（真 token、真 Telegram；`docker logs`，同步缓冲已生效）

```
[T3.1] 天狗骰子 bot 启动中…（token_key=TELEGRAM_BOT_TOKEN_TEST，值不打印）
[T3.1] 主轨菜单已注册：/start /help /settings /roll /nd /system /secret /bank /ct /log
[T3.1] @username="example_dice_bot"；路由=slash 主轨 + 裸 ASCII 辅助轨 + 按钮回调分支
[T3.5] 已挂 handler：…；菜单十条命令全部有真身
[T3.2]/[T3.4]/[T3.1] 暗骰/[T3.5] log/[T2.6] ×2 …（完整见证据文件）
```

- 「菜单注册成功」行是 `register_main_commands` **之后**才打印的（失败即 `exit 1`）→ 该行出现 = setMyCommands 已被 Telegram 接受。
- 长轮询证据：容器 netns `/proc/net/tcp` 有 `ESTABLISHED(01)` 到 `<telegram-api-ip>:443`（Telegram）；容器持续 Up。
- 数据卷：`tengu.db`+WAL+SHM 在 `/opt/<project>/data-smoke/` 生成（uid 1000，uid 映射正确）。

### 5.3 restart 策略（`--restart unless-stopped`，实测语义三分）

| 场景 | 实测 | 结论 |
|------|------|------|
| **主进程死亡**（宿主侧 `kill -9` 容器 init；容器内信号对 PID1 被内核丢弃——见 §8 坑 3） | `State=running RestartCount=1`；启动序列出现 **2 次**；复跑后新 ESTAB 连接 | ✅ 策略自动拉起（计划 §8「容器内 kill 主进程后自动拉起」的实现口径） |
| `docker kill` / `docker stop`（手动停止） | `State=exited`，RestartCount 不变（kill 后 `docker start` 可手动恢复；起后回 `running`） | ✅ 手动停止不自动拉起——`unless-stopped` 的**正确契约**（官方文档；对照容器实测验同） |
| 进程非零退出（对照容器 `exit 1` 循环） | `RestartCount=3` | ✅ 崩溃循环亦被策略接管 |

### 5.4 清理与 dev bot 恢复

- 冒烟容器两次执行后均 `docker rm -f`；`docker ps -a` 无残留（验收「不留跑着的测试实例」）。
- dev bot 全程**同一 pid（<pid>）存活**：两轮「SIGSTOP→SIGCONT」后状态 `Ssl`，并各自恢复 `ESTABLISHED → <telegram-api-ip>:443`（实测新端口 <port>/<port>）——未 kill、未重启、未换进程。
- 冒烟未向任何群发送消息（`LOG_ROLLS=0`、无入站 update 处理日志）；测试环境被动收信风险已按任务口径接受。

## 6. 启动 / 重启命令与日志轮转（验收 #2 附项）

**正式容器（T4.5 上线用；前置：用户把 `.env` 填进 `/opt/<project>/data/`）**：

```
sudo docker run -d \
  --name tengu-bcdice-tg \
  --restart unless-stopped \
  --log-opt max-size=10m --log-opt max-file=3 \
  -v /opt/<project>/data:/app/data \
  tengu-bcdice-tg:latest
```

冒烟命令 = 上面 + `--name tengu-bcdice-tg-smoke` + `-e TENGU_ENV=test -e DB_PATH=/app/data/tengu.db --env-file <repo>/.env -v /opt/<project>/data-smoke:/app/data`
（token 只经 `--env-file` 注入，不经 argv/脚本/文件拷贝）。

**日志轮转口径（择一并记录理由）**：逐容器 `--log-opt max-size=10m --log-opt max-file=3`（driver=json-file 默认）。
选择理由：daemon 侧（`/etc/docker/daemon.json` 默认 log-opts）需要**重启 dockerd**，
而本机同时跑着若干无关服务，
blast radius 不值；逐容器参数随部署命令走、只作用于本项目。实测
`LogConfig=json-file map[max-file:3 max-size:10m]`，实体文件
`/var/lib/docker/containers/<id>/<id>-json.log` 存在。上限 ≈ 30MB 轮转保留
（运营日志；跑团 log 是显式 /log 录制，不受影响）。

**重启/停止**：`sudo docker restart tengu-bcdice-tg`（重启后全功能照跑——冒烟已实证重跑启动序列）；`docker stop` 为手动停止（保持停止），`docker start` 手动拉起。

## 8. 实现级决策清单（速览）

1. 三阶段（builder/gems/runtime）：生产 bundle 单独装（不含 :test），runtime 与 builder 解耦。
2. bundler 钉 4.0.22 + `BUNDLE_FROZEN=true`：只吃 Gemfile.lock，漂移即失败（R9）。
3. 基底 ruby:3.4-slim（Debian 13 / ruby 3.4.11，与 lock 平台 `x86_64-linux-gnu` 匹配，sqlite3 预编译版开箱即用）。
4. runtime 只 COPY 显式子集（bot/db/lib/game_systems/i18n + Gemfile.lock）——test/references/scripts/docs 不进运行镜像。
5. 非 root：`tengu` uid/gid 1000 ↔ 宿主 <deploy-user> uid 1000，卷内文件互操作实测无碍。
6. `TELEGRAM_ENV_FILE=/app/data/.env`（镜像 ENV）：生产 .env 只住数据卷；镜像内无 .env（.dockerignore 双保险）。
7. stdout/stderr 同步下沉到 `bot/main.rb`（非 TTY 实时日志，任何入口形态均生效）。
8. 日志轮转走逐容器 `--log-opt`（理由见 §6），不动 daemon.json。
9. 重启策略只落在 `docker run --restart unless-stopped`（镜像不写死策略）。
10. 冒烟保护性时序（SIGSTOP→过期→独占→CONT）：保护同 token 的 dev bot 免于 409 崩溃链。

### 实测坑（留档，OPERATIONS 会引用）

1. **匹配语义**：rsync 与 .dockerignore 的裸 `data/` 模式都会匹配 `test/data/`（任意深度）→ 两侧统一 `/` 锚定；锚定后的行为已用 6 变体探针实测。
2. **本机 legacy builder**：无 `--progress`/buildx；`--no-cache` + 日志重定向即取证方案。
3. **PID1 信号**：容器内进程对 PID1 的信号（含 SIGKILL）被内核丢弃（实测 `rc=0` 而进程存活）→ 「kill 主进程」模拟必须自宿主侧；`docker kill/stop` 是手动停止语义（不自动拉起）。
4. `docker stop` 本栈退出码为 1（ruby 对 SIGTERM 的默认行为；对照纯 ruby 容器复现）——仅记录，不影响策略（手动停即保持停）。
