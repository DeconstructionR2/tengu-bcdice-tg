## 2. 设计决策落点（实现级）

### 2.1 E5：清理策略 = 公开后删 + 惰性 TTL（两条都做）

E5 给了两个方向，本任务两条都做：

- **公开成功后删行**（语义正确的那条：结果已公开，行留着就是无主残留）
  - **删除放在发送成功之后**：发送失败时行还在 → 用户可再按一次（或 `/secret last`
    重取），不会出现「按钮提示已公开、库里也没了、群里其实没有这条」。
- **惰性 TTL：每次写入时顺手删 `created_at` 早于 7 天的行**，**不建定时任务**。
  理由：本服务是单文件 SQLite + 单进程长轮询，**没有调度器**；为一个「每天每人
  几次」的表引入常驻执行路径（要处理停机补跑/并发/重入）不值得，而写入时顺手扫
  一次的小表代价可忽略。
  - **已知性质（非缺陷，是权衡）**：没有写入就没有清理。只掷暗骰不点按钮的用户会让
    过期行滞留到「下一次有人掷暗骰」为止。过期行的授权仍受 `user_id` 约束，且 TTL
    远长于 ephemeral 生命周期，对本表语义无害。
  - **TTL = 7 天**：`/secret last` 的价值恰恰在「跑团中途/当天忘了结果」，取更长
    与「未公开的私密结果不长期留存」的隐私直觉冲突；7 天 = 覆盖一个自然周。

### 2.2 callback_data 命名空间：`sec:` 前缀

- 形如 `sec:3f9c2e1a4b7d8e05`，**20 字节**，距平台 64 字节上限极远。
- 为什么必须有前缀：callback_data 是**一根共享的线上总线**，本项目将来还会长出别的
  按钮（T3.2 银行 / T3.4 自定义表 / T3.5 log）。裸 id 一旦撞上别的命名空间，按钮会去
  别的表捞数据；反过来别的命名空间的后门拿到本表的 id 就能凭空公开一条暗骰。
- **反解 fail-closed**：`secret_id_from_callback_data` 对任何非本前缀 / 畸形数据段
  （长度不对、非小写十六进制）一律返回 nil，绝不「猜着捞一把」。测试钉了 11 种拒绝输入。
- **id 形态**：16 位小写十六进制（64 bit 熵）。不用 base36/base62 是为免大小写歧义——
  callback_data 会走一遍 URL / 日志 / 手抄，大小写混淆过的 id 会变成查不到。

### 2.3 三条不可让步的纪律

1. **结果永不走普通消息。** `SecretDiceHandler#call` **恒返回 nil**：router 的契约是
   「handler 返回 String 就代发」，只要返回结果文本，暗骰就会广播进群。返回 nil 是
   **结构性**保证，不靠逐处 if。
2. **先答回调，再干活。** router 在 context 里备一个**幂等**的应答闭包（首次生效，
   后续 no-op），handler 在落库/发消息之前先答。`dispatch_callback_query` 的
   `ensure` 里还有一层兜底：handler 抛异常被 `run_handler` 的 rescue 吞掉时补答，
   客户端不会永远转圈。
3. **权限只看真人 user_id。** `secrets.user_id == query.from.id`，不查群管理员名单——
   Telegram 的匿名管理员消息没有 `from`，天然规避该坑（§0.2.4）。

### 2.4 其它落点

- **`/secret last` 复用原行，不新建**：last 是「重看」不是「再掷」。复用 id 意味着按钮
  还是同一个（同一份授权），且不额外制造 secrets 行（否则每次 last 都把 TTL 往后推、
  绕过 E5 的清理语义）。
- **`latest_for` 作用域 = (chat_id, user_id)**：跨群的 id 不该互相可见；公开时用的
  本来就是**记录里的** chat_id/thread_id 原地回发，「在哪掷的就在哪取回」也符合心智。
  同秒并列用 `rowid DESC` 兜底（`created_at` 只到秒）。
- **拿不到 user_id / chat_id 就完全静默**：既发不出 ephemeral，也不该发普通消息。
- **`thread_id` 按记录里的原值存**（未归一）：公开时原样透传给 Telegram；nil → 0 = 群级，
  与 E4 同尺度。
- **规则系统走 /roll 同一套三级查找**（话题 → 群 → 全局默认 NinjaSlayer2Ex）：暗骰不是
  「另一个规则世界」，掷什么由本群设置决定，只有**投递方式**是私密的。

## 3. 接缝（必须对着 vendor 真实形状写）

`bot/router.rb` 的 `dispatch` 新分支在 `extract_message` **之前**——后者显式跳过
CallbackQuery 形状（否则按一次「公开」会被当成「原消息被重发」二次路由，原消息文本
若恰好是骰式就白掷一次骰，commit 41f3c58 的教训）。

按 gem 2.8.1 源码核实的事实：
- `Client#listen` yield 的是 `handle_update` 的返回值 = `update.current_message`；
  `callback_query` update 的 `current_message` 就是 **CallbackQuery 本体**
  （`types/callback_query.rb`：必填 `id` / `from` / `chat_instance`，可选 `message` / `data`）。
- `Api::ENDPOINTS` 含 `answerCallbackQuery` → gem 原生方法名可用（`answer_callback_query`）；
  仍保留与 `send_one` 同款的 raw 降级（只认 receiver == api 本体）。
- `InlineKeyboardMarkup`/`InlineKeyboardButton` 经 `jsonify_value` → `to_json` 自动序列化
  成 Bot API 要的 `inline_keyboard` 形状（实测 `"sec:..."` 原样进 JSON）。

`test/bot/test_listen_seam_test.rb` 的新增 3 条按**真实形状**走 `TelegramApi#start` →
`Router`：正向断言回调到达 `:callback_query` handler 且 context 带 `id`/`data`/`from`/
`answer_callback_query`，以及默认应答真的发出 `answerCallbackQuery`。

### 实施期实测发现的两个接线缺口（都已被测试钉住）

1. **`send_ephemeral` 不透传 extra**：原签名无 `**extra`，`reply_markup` 被 ArgumentError
   吞掉（且被 handler 的 rescue 静默）。已加 `**extra`。
2. **`run_handler` 没把 `data` 摊进 context**：handler 读 `context[:data]` 拿到 nil，
   整条公开路径静默失效（只被 router 的 ensure 兜底应答掩盖）。已在 `run_handler` 里
   显式摊平；`SecretDiceHandler#call` 也改成**按 kind 分发**而非只按 name。

> 教训泛化（T2.6 接缝事故同款）：同一个 handler 对象挂在两个注册键上时，**必须验两个键
> 都真的被调用**——只测单元会漏掉「看着接了实则从不执行」。

## 5. 遗留风险 / 待真机验收

1. **ephemeral 消息上的内联按钮，客户端行为待真机确认**（最高优先）。本实现的依据是
   T2.2 的服务端实证（`sendMessage` + `ephemeral_message_parameters` 被接受，回执
   `message_id=0` + `ephemeral_message_id`；`editEphemeralMessageText` 实时生效），
   但**「ephemeral 消息里能不能带 inline_keyboard、客户端会不会渲染那个按钮」从未
   在真机验过**。若客户端不渲染按钮，本设计的「公开」入口就只剩 `/secret last` 重取，
   需要在 Phase 4 前补一次真机探针。
2. **`answerCallbackQuery` 未在真机验过**（T2.2 的报告里明确列为「未单独探」，
   原文：「callback_query 路径的 ephemeral 未单独探——T3.1 实现「公开」按钮时顺带验证」）。
   gem 白名单收录该端点是源码核实，不等于服务端接受我们的参数组合。
3. **ephemeral 消息 ID 与按钮的绑定**：公开时我们用的是**记录里的 chat_id/thread_id**
   而不是按钮所附原消息的位置。若原消息已被删除、或用户换话题后按了按钮（按钮随
   ephemeral 消息一起消失，实际很难发生），结果会发到记录位置而非按钮位置。这是**刻意**
   的（记录位置是掷骰时的作用域，符合用户心智），但真机需确认没有违和感。
4. **`callback_query.message` 可能指向不可访问消息**（`MaybeInaccessibleMessage`）：我们
   **完全不读** `message` 属性，只用 `data` + `from`，故不受影响；但若将来做「编辑原
   ephemeral 消息」的增强，这条要重新评估。
5. **单进程轮询下的竞态**：两个人同时按同一个按钮 → 两条 update 顺序处理，第一个删行、
   第二个查到 nil 并回「已过期」。这是**正确**行为（不会重复公开），但真机上第二条
   的 toast 文案「已过期」对用户略生硬。
6. **TTL 无定时器**：见 §2.1。只掷不看的用户会让过期行滞留到下次写入。若将来 secrets
   写入频率上来（或表显著变大），应重新评估加一个真正的清理路径。
7. **20 条/分滑窗限流仍未实现**（T2.6 遗留观察项）：暗骰与公开都会增加发送次数，
   但相对 20 条/分的群限额仍是低频，暂不构成压力。
8. **未跑真机**：本次全程 mock，**不读 .env token、不发真消息、不起 bot 进程**
   （仓库里在跑的测试 bot 进程未被 kill/重启）。
