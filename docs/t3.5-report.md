## 2. 架构落点：录制挂钩的位置与理由

### 2.1 两处集中点（各自唯一）

```
入站 update
  │
  ├─ callback_query？──────► dispatch_callback_query（按钮路径，不进录制）
  │
  ├─ extract_message → nil？（编辑消息等）────► 跳过（不进录制）
  │
  ├─ 迁移服务消息？───────► handle_migration（不进录制）
  │
  ├─ chat/chat_id/thread_id 就位
  │      │
  │      ▼
  │   ★挂钩① record_incoming（router → 注入的 session_log 对象）
  │      ├─ /secret 命令消息 → 显式排除（见 §4 决策 1）
  │      ├─ 文本消息（命令/闲聊一视同仁）→ 落 msg_kind=text
  │      ├─ 非文本媒体 → 落 msg_kind=<photo|voice|…> + 中文占位
  │      └─ 服务消息/无内容 → 不录
  │      │
  │      ├─ slash 主轨 / aux 辅助轨 → handler
  │      │       │
  │      │       ▼
  │      │   ★挂钩② run_handler 的「返回 String → router 代发」分支
  │      │       └─ 代发原文逐字落 is_bot=1（暗骰结果结构性到不了这里）
  │      │
  │      └─ 不命中任何轨（闲聊）→ 不回复（但已录）
  ▼
（消息处理结束）
```

**位置理由（逐条）**：

| 决定 | 理由 |
|---|---|
| 挂钩①放在 `dispatch` 内、`text.nil?` 早退**之前** | 非文本消息与「不命中任何轨的闲聊」都在此处被丢弃——挂钩不提前就永远录不到（「此前只把命令喂给 handler」的补齐点） |
| 挂钩①放在迁移分流**之后** | 迁移服务消息是系统噪声且有自己的处理路径，不进录制 |
| 挂钩不放进 handler | 闲聊不经过任何 handler——只有 router 的 dispatch 是「全部消息」的必经点 |
| 挂钩②放在 `run_handler` 代发分支 | 「bot 自己的输出」在此有唯一定义：router 代发的 handler 返回值。放在这里等于「群里实际发出的文本 = 录进 log 的文本」（测试钉住逐字一致） |
| 回调/编辑消息不进录制 | dispatch 分流顺序与 `extract_message` 既有守卫天然覆盖（回归测试钉住三类 update 零条目） |
| **router 仍然不碰 DB/不联网** | 挂钩只调注入的 `session_log:` 对象（默认 nil = 零开销直落）；DB 全在 `bot/session_log_recorder.rb` 里。既有纪律不破，既有用例零改动 |

### 2.2 数据流与 seq

- `session_log_recorder` 收到消息 → 问 DB 层「本作用域 (chat_id, thread_id 归一)
  有没有**正在录**的 log」→ 有则 `append_entry`（**seq 在 :immediate 事务内
  现算** `COALESCE(MAX(seq),0)+1`，单连接 + 事务双保险）。
- seq 序 = 事件序：用户消息先录（挂钩①先于 handler 执行），bot 输出后录
  （挂钩②在代发处）——单线程长轮询下确定性成立；导出按 seq 升序且**不重排**
  （渲染层信任 DB 排序，测试钉住「导出序 == seq 序」）。
- 录制故障（store 抛异常）由 router 挂钩 rescue + warn——**不杀消息处理**
  （掷骰/查账照常；测试：store 炸时 `/roll SB` 照样回发）。
- 未注入 `session_log:`（全部既有单测）→ 钩子零行为。

## 3. 导出格式（样例）

`/log end` 时按同一份数据渲染两个文件，`send_document` 发回 log 自己的
`(chat_id, thread_id)`；文件名 `tengu-log-<id>.txt` / `.json`（经 T3.5 修复的
`filename` 透传上 wire），临时目录发完即删。

### txt（可读转录，逐行序 = seq 序）

```
===== 跑团 log：第一次跑团 =====
作用域：群 -1001234567890 / 话题 2468
时间段：2026-10-12 04:00:01 ～ 2026-10-12 05:00:03
条目数：5
-----
[0001] 2026-10-12 04:00:02 [bot] example_dice_bot：已开始录制「第一次跑团」（log #1）。本话题的消息将开始记录；/log off 暂停，/log end 结束并导出。
[0002] 2026-10-12 04:00:10 山田：我们开始吧
[0003] 2026-10-12 04:00:15 山田：/nd SB
[0004] 2026-10-12 04:00:15 [bot] example_dice_bot：サツバツ!!(6) ＞ 「さらばだ！ イイイヤアアアアーーーーッ！」ヤリめいたチョップが敵の胸を貫通！ ゴウランガ！ 
[0005] 2026-10-12 04:00:20 山田：（照片）
```

- 头部 5 行：标题 / 作用域（群级不带「/ 话题 N」）/ 时间段（created_at ～ ended_at）/
  条目数 / 分隔线。
- 条目行 `[%04d] 时间 [bot ]名：内容`——bot 条目在名字前有 `[bot] ` 标记；
  内容**逐字**（多行结果保持原样换行，不做折行/转义）。
- 非文本条目内容即中文占位符（`（照片）`/`（贴纸）`/`（语音）`…），`msg_kind`
  以英文种类落 json。

### json（结构化）

```json
{
  "format": "tengu-bcdice-tg/session-log",
  "version": 1,
  "log": {
    "id": 1,
    "name": "第一次跑团",
    "chat_id": -1001234567890,
    "thread_id": 2468,
    "status": "ended",
    "created_at": "2026-10-12 04:00:01",
    "ended_at": "2026-10-12 05:00:03"
  },
  "entries": [
    { "seq": 1, "sender_name": "example_dice_bot", "user_id": null, "is_bot": true,
      "msg_kind": "text", "content": "已开始录制…", "created_at": "2026-10-12 04:00:02" },
    { "seq": 2, "sender_name": "山田", "user_id": 42, "is_bot": false,
      "msg_kind": "text", "content": "我们开始吧", "created_at": "2026-10-12 04:00:10" }
  ]
}
```

- `is_bot` 在 json 里是布尔（落库形态是 0/1）；`user_id` bot 条目为 null。
- 通用文本口径（计划定案）；专用染色器格式适配（海豹染色器等）留 backlog。

## 4. 实现级决策清单

1. **暗骰处置（任务书要求选定并写明）**：**不记「（暗骰）」占位、命令消息也不录**。
   - `/secret` 命令消息：**不落盘**（router 的 `secret_command_text?` 显式排除，
     含 `/secret@bot` 变体、大小写不敏感——宁多排不漏排）。理由：Bot API 10.3
     的 `is_ephemeral` 命令**群内不可见**，录进去等于把「某人刚做了暗骰、用的
     哪条骰式」写进导出文件；占位同理（泄露「此处发生过暗骰」这一元信息）。
     防泄纪律 > 录制完整度（R8）。
   - 暗骰**结果**：SecretDiceHandler 恒返回 nil（自走 ephemeral），结构性地不
     经过 run_handler 代发分支——挂钩②对它**不可达**，不靠 if 判断。
   - 裸 `S2d6`（辅助轨 S 前缀暗骰）：**输入**照录（它本身是群内可见消息），
     **结果**不录（DiceHandler 对 secret 结果静默返回 nil，同样结构性）。
   - 负向钉测试：录制中执行 `/secret` 条目数不变、结果文本绝不在库/导出中；
     裸 `S2d6` 秘密结果同款。
2. **「到达时正在录」语义**：录用与否在**消息到达时刻**的状态上判定——
   `/log off` 命令在暂停生效前到达 → 录；`/log off` 回执发送时已暂停 → 不录；
   `/log on` 命令到达时还在暂停中 → 不录；恢复回执 → 录；`/log end` 命令在
   finish 生效前到达 → 录进最后一条；结束回执 → 不录。测试按此逐条钉住
   （与验收词「recording 中命令都落」严格一致）。
3. **同作用域互斥**：进行中（recording/paused）只允许一条；`/log new` 撞上
   回「已有进行中的录制「X」」并指路 `/log end`（不静默顶替）。ended 是终态，
   旧的留在库里供 `/log list`。
4. **paused 可直接 `/log end`**（不要求先 on 再 end；用户暂停到一半想收工是常态）。
5. **服务消息不录**：只有「用户可发送的内容型消息」（文本 + 媒体占位）进录制；
   入群/置顶/改名/话题创建等不录（噪声）。带图带字的消息**只记占位符**，
   caption 不单独提取（口径「非文本记占位符」的字面义；避免「半条文本」歧义）。
6. **名字校验**：strip 后非空、≤100 字符、不含控制字符（`\n` 会拆坏回显与导出
   头部）；其余一律 `:invalid_name` 拒收不落库。
7. **导出文件名与 `filename` 透传**：`telegram_api.rb#send_document` 的 `filename`
   形参此前从未进 params（临时路径的随机名会原样上 wire）——T3.5 修复并补测试。
8. **/log 不做权限门槛**（任何人可开录）——R8 的隐私边界靠「显式 `/log new`
   才开录 + 开录/暂停/结束群内明示 + 主开关 + 文件只回原作用域」四件套，而不是
   权限（录的是本群自己说的话；管理员门槛会挡住正常跑团使用）。
9. **/log list 上限 10 条**（最新在前，带各 log 状态与条目数），超出只提示
   「更早的未列出」——不刷屏。
10. **bot 条目显示名**：注入 `bot_name`（main.rb 取 get_me 的 username，失败退
    「骰子bot」）。bot 输出不因发送失败而回滚记录（记录的是「bot 产出的回复」；
    发送失败本身有 warn 与回执兜底）。
11. **导出失败不伪装**：`/log end` 已把状态置 ended（数据都在库里），文件发送
    失败时回执明说「导出文件发送失败——录制数据已保留」，绝不报「已发送」。
12. **thread 归一**：导出用 log 的归一后 thread_id（0=群级 → 不发
    `message_thread_id`；General=1 → 归一 0 → 同群级）。与 T3.1 评审修的
    「0→nil 防 forum 群 400」同一纪律。

## 6. 遗留风险 / 后续

1. **真机未验证**（零联网纪律）：document 上传在真 Bot API 的 multipart 行为、
   手机端文件名的呈现——留 Phase 4 真机验收（`/log end` 是验收清单里的
   「log 导出」项）。
2. **20 条/分滑窗未实现**（T2.1 留档的既有观察项，本任务未动）：`/log end` 会
   连发 3 条（txt、json、回执），1 条/秒配速已覆盖「每秒」限额，分钟级限额
   在极端连续操作下有理论 429 面。风险低，登记为既有缺口。
3. **导出失败无聊天层重试入口**：计划的命令集恰为 new/on/off/end/list 五个，
   未加 `/log export <id>`；数据在库里不丢，但用户拿不到文件时需要人工重发。
   建议 backlog：`/log export <id>`（管理或本人）重发导出。
4. **编辑/删除消息不反映**：log 是「事件流」不是「当前群状态镜像」——编辑不
   重录（保留原始版本）、删消息不从 log 里去掉。若未来要镜像语义需另设计。
5. **caption 不录 + 服务消息不录**：口径见 §4 决策 5；若未来要「完整转录」
   需扩 KIND_PLACEHOLDERS 与 caption 提取。
6. **/log list 不分页**（上限 10 条 + 溢出提示）；log 行数长期累积未加清理
   （量极小；与 secrets 的 TTL 策略不同——录制是用户显式要保存的资产，默认不删）。
7. **暗骰占位口径**：选定「不记」。若用户日后希望 log 里能看出「此处发生过
   暗骰」，需改口径（一行改动 + 测试），登记备查。
8. **染色器格式**：专用格式（海豹染色器等）适配按计划留 backlog。
