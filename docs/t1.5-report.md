## 1. kimi-code T1.5 评审预警逐条落实

### 预警 1：无 datarange/+x 的表绝不钳制 —— ✅ 落实

先查 ledger 确认前提（`references/extracted/i18n_key_ledger.yml`）：

```
NJI/NJS/NJN/NJC: datarange: null,  dice: {a: 1d6},  item_count 6
NJK/NJB:         datarange: null,  dice: {a: 1d36}, item_count 36
```

**6 表全部 `datarange: null`，与预警预期一致。**

再从源码链条独立验证「为什么不钳制」——不是「表里没写 datarange 所以不钳制」，而是**天狗的钳制分支根本不会进**：

- `references/src/TenguDiceBot/.../tengu_dice/NJDiscordReply.js:91-97`：
  ```js
  if (diceroll.isTableAdditionValue) {
      if (datarange.max < sumall) tableString = data[datarange.max];   // 钳制
      else if (datarange.min > sumall) tableString = data[datarange.min];
      else tableString = data[sumall];
  } else tableString = data[diceroll.sumall];   // ← 本批走这条
  ```
- `classes/SearchTableDiceroll.js:56-77`：`isTableAdditionValue = true` 只在 `/\+x/.test(diceStr)` 为真时置位。

本批 6 表的 dice 字面量是 `"1d6"` / `"1d36"`，**不含 `+x`** → `isTableAdditionValue` 恒 false → 直接 `data[出目]`，与 ledger 的 `datarange: null` 完全自洽。

**因此实现上刻意不复用 `proc_karmarond` 的钳制骨架**：

| | 卡尔马（T1.4） | キャラメイク（T1.5） |
|---|---|---|
| datarange | 1..12 / 1..6 | 无 |
| 越界行为 | **钳到端点**并标注 `(raw→clamped)（クランプ）` | **不响应** |
| 代码常量 | `KARMAROND_DATARANGE` | **刻意不设**（凭空造边界是假信息） |

实测对照（同一骰序，同一实现）：

```
KRS_A@99  → ソウカイヤカルマロンダリング(1D3) ＞ (100→12)（クランプ） ＞ ...
NJI@99    → (不响应)
```

该铁律已**常驻化**：`gen_table_toml.rb` 的 `cross_validate!` 与 `ledger_consistency_test.rb` 各自断言 `entry(key)["datarange"].nil?`；一旦有人给这 6 表加 datarange，两处立刻红。

另有一条更强的派生断言：**掷骰可达域 == items 数**（无钳制时二者必须恒等，否则出目会落到 items 外）。已进 `test_chara_make_reachable_domain_matches_items`。

### 预警 2：d36 语义必须先实证 —— ✅ 落实，结论是**单颗 36 面**

用 Node 直接 require 钉版快照（只读，未改动）：

```js
const Dice = require('references/src/TenguDiceBot/TenguDiceBot/classes/dice.js');
// 300 次掷骰，统计 resArray 长度
resArray length histogram: {"1": 300}          // 恒为 1 颗
sample: toString=(1)  sum=1  tranced=1d36  resArray=[1]
// 5000 次掷骰的 sum 取值域
1d36 sum range over 5000 rolls: 1 .. 36
util.checkSintax(1,36)? true
```

**结论：`1d36` 是单颗 36 面骰，不是 D66（6×6 组合表）。**

补充交叉证据（防"实测只证明了一种可能"）：

1. 全仓 `d66Option` 只有 **一处**判断（`NJDiscordReply.js:83`），而 `nd_datatable.js` 里**没有任何一张表**声明该字段。若 1D36 走 D66，必须有 `d66Option: true`，实测 6 表全为 `undefined`。
2. 若走 D66，出目域会是 11..66 或 1..36 经 `6a+b` 换算；实测 dice.js 的 `resArray` 恒长 1、`sum` 直接落在 1..36，中间没有任何换算步骤。

→ Ruby 侧实现为 `times: 1, sides: 36`，索引 `items[sum - 1]`，**不存在** D66 式 11..66 → 1..36 映射。

该结论已常驻化为 `test_d36_is_single_36_sided_die_not_d66`：同时锁死 `times == 1`、`sides == 36`、ledger `dice.a == "1d36"`。日后若有人误按 D66 实现（times 变 2），断言立刻红。

## 3. 阻塞级发现：`SEISEN` 前缀与 BCDice 暗骰标记冲突

### 现象

`SEISEN9` **完全不响应**，但直接调用 `eval_game_system_specific_command("SEISEN9")` 一切正常。

### 根因（逐步实证）

`base.rb:47` 把前缀数组**原样**拼进正则（不转义）：

```ruby
@prefixes_pattern = /^(S)?(UH|[KENHU]|SB|WS|WSE|NRS|NSRS|...|SEISEN)/i
```

两步连锁：

1. 可选的 `(S)?` 是 BCDice 的**暗骰标记**。正则回溯**优先**让 `(S)?` 匹配掉 `SEISEN9` 的首字母 `S`。
2. 剩下 `EISEN9` 交给前缀组 —— 而 `[KENHU]` 这个**字面量**被当成**字符类**（父类 `register_prefix("[KENHU]")` 的既有语义），其中的 `E` 恰好匹配 `EISEN9` 的 `E`。
3. `base.rb:254-255` 因 `m[1]` 非 nil 判定为暗骰命令，`command = command[1..-1]` → 命令变成 `EISEN9` → 本类正则全部失配。

实测证据（`enable_debug` 打印的真实入参）：

```
input: EISEN9                       ← S 被吃掉
[dbg] proc_ex_command => NilClass
[dbg] super => NilClass
eval -> nil
```

### 影响面审计

逐条比对全部既有命令的 secret 标志，**无一受影响**：

```
SB@3 secret=false | SWSX secret=true | SNJI secret=true | NSRS_A secret=false
KRS_A secret=false | SKRS_A secret=true | NJI secret=false | SNJI secret=true
```

- `SWSX` / `SNJI` 是**正常**的：父类 `WS` 与本类 `NJI` 不以 S 开头，`S` 确实是暗骰标记。
- 只有 `SEISEN` 是"真 S 开头被误吃"。
- `[KENHU]` 字符类怪癖是上游既有行为（父类单独跑 `[KENHU]1` / `KENHU1` 也是 nil），原样保留。

### 处置

覆写 `self.prefixes_pattern`，在父类原正则**前**追加 `SEISEN` 优先分支：

```ruby
def self.prefixes_pattern
  @prefixes_pattern ||= Regexp.new("\\A(?:SEISEN|#{super.source})", Regexp::IGNORECASE).freeze
end
```

效果：

- `SEISEN9` → 由新分支整体匹配，`m[1]` 为 nil → secret=false，命令原样传下去 ✅
- `SSEISEN9` → `(S)?` 吃掉第二个 S → secret=true，暗骰能力**保留** ✅
- 其余前缀直接展开父类 `source`（不重新拼），secret 行为**逐字节同源** ✅
- 父类 `@prefixes_pattern` 缓存不受影响（类实例变量沿继承链独立）✅

已逐条实测：

```
SEISEN9    → secret=false 判定成功！
SSEISEN9   → secret=true  判定成功！
SBX        → secret=false
SSBX       → secret=true
父类 NinjaSlayer2: prefixes_pattern 未变
```

### 为何不用 `change_text`

上游 `NinjaSlayer.rb:82` 有 `change_text` 惯用法，但它在本例中不合适：`change_text` 的输出会**再经 upcase**，且必须自行改写成能通过 `prefixes_pattern` 的形状 —— 为一个前缀做字符串级手术，风险面大于直接修正前缀正则本身。

## 5. 意外发现 1（数据管线缺陷）：重跑生成器会**静默丢弃 2 张表的 ledger 条目

### 现象

T1.5 需要重新生成 ledger（新增 SEISEN 段）。跑 `json_to_i18n.rb` 后：

```
⚠ 键 NSRS 已存在且内容不同，**未覆盖**（请人工裁决）
⚠ 键 NJI 已存在且内容不同，**未覆盖**（请人工裁决）
$ git diff --stat
 references/extracted/i18n_key_ledger.yml | 87 +--------------------------
 1 file changed, 1 insertion(+), 86 deletions(-)
```

**ledger 从 25 条掉到 23 条，NSRS 与 NJI 的条目整条消失。**

### 根因

T1.3 引入了 `TEXT_REWRITE`（表文本内嵌命令引用 ASCII 化），yml 里存的是 `rewrite_items(src["items"])`；但**幂等守卫仍拿它与 JSON 原文 `src["items"]` 比**：

```ruby
# scripts/json_to_i18n.rb（修复前）
if existing && existing["items"] != src["items"]   # ← 比原文，必然不等
  already << "⚠ 键 #{key} 已存在且内容不同，**未覆盖**"
  next                                                  # ← 该表的 ledger 条目也被跳过
end
```

凡命中改写的表恒被判"内容不同"→ `next` → 表不写、**ledger 条目一并丢失**。对照 §6 逐字回读自检（那里比的就是 `rewrite_items(...)`），可见守卫漏改。

这是一个**已存在的潜在事故**：只要有人重跑生成器，NSRS/NJI 的台账就会消失，而当时所有测试仍是绿的（没有断言 ledger 条目数）。

### 修复

```ruby
if existing && existing["items"] != rewrite_items(src["items"])
```

对齐自检写法。修复后：`2版 14 张`（原 12 张）、ledger 25 条完整、`git diff references/` **零改动**。

**这条同时意味着 T1.5 的 yml/ledger 变更仅有 11 行新增（judge 段），没有任何既有数据被改动。**

## 7. 意外发现 2（生成器陷阱）：`%w[]` 吞掉注释，产出**非法 toml**

### 现象

异常系最初写成 `%w[...]` 并在元素之间插了 `# 注释` 行。`%w` 按空白切分、**不认 `#`**，于是这行变成了一个字面命令：

```toml
# 前导零：是字符串键直查，"03" 不响应
[[ test ]]
input = "是字符串键直查，"03""      ← 非法 toml，整个套件炸
```

`Tomlrb::ParseError: parse error on value "03" (IDENTIFIER)`

### 为什么没被现有自检拦住

`generate_error_cases` 的"真的不响应"自检**照样通过**（垃圾串当然不响应）—— 即**静默产出坏文件**，等到 runner 解析时才炸。

### 修复

1. `T15_ERROR_CASES` 改用显式字符串数组（注释可以安全地放在元素之间）。
2. 加**字符集守卫**：条目必须匹配 `/\A[A-Za-z0-9_@.!＋+\-！]+( +…)*\z/`，否则 abort。
   - 允许全角 `！`：`SEISEN！9` 是**有意**的用例（天狗 WASSHOI 收 `！` 而 SEISEN 不收）。

## 8. 意外发现 3（Ruby 陷阱）：负下标让"越界断言"假红

`test_chara_make_fixed_index_bounds` 初版用 `items[min_i - 2]`（即 `items[-1]`）表达"下界之外应为 nil"：

```
Failure: expected to be nil.
  <"**プレイヤーは1〜5の中から好きなジツを選んでよい**…">   ← 这是 items 的最后一项
```

**Ruby 负下标会绕回数组末尾**，`items[-1]` 返回最后一项而非 nil。

修复：越界探测只用**正下标** `items[items.length]`，下界侧改断言索引算术（`0 - min_index < 0`），不去索引数组。该陷阱已在代码注释里留档。

另有一处：`I18n.t("...judge.SEISEN")` 取子树返回的是**符号键** Hash，`yml_judge["judge_name"]` 恒 nil —— 改用 `yml_judge[:judge_name]`。
