## 2. 备份脚本（scripts/backup.sh）

行为表：

| 场景 | 行为 | 退出码 |
|------|------|--------|
| DB 不存在（T4.5 上线前） | stdout 一行：`跳过——DB 不存在（…，未上线或尚未生成）`；不创建备份目录 | 0 |
| DB 存在 | `sqlite3 "$DB" ".backup '$BACKUP_DIR/tengu-YYYYMMDD.db'"`（在线一致，免停容器）；同日重跑先删旧同名（幂等）；备份后 `PRAGMA integrity_check` 自检 | 0 |
| 保留 | 只清理严格形态 `tengu-[0-9]{8}.db` 中超出最近 7 份者（字名字典序=时间序）；目录内其他文件（含 `tengu-manual.db`、`*.db.old` 等）不动 | 0 |
| 失败（sqlite3 非零 / 目录不可写 / 完整性不过） | 半成品当场删除（防「假新鲜」掩盖告警）+ stderr 结构性 ERROR 行 | 1 |

- 环境变量覆盖：`TENGU_DB_PATH` / `TENGU_BACKUP_DIR`（缺省为生产路径；干跑不碰生产）。
- 告警路径分工（计划口径）：脚本自身不投递；cron stderr 进 `backup.log` 留档，监控侧
  由「备份新鲜度」检查兜底（§4）——即备份连续失败 → 无新文件 → 36h 后监控告警。
- **部署形态决策：cron 直调 repo 路径** `<repo-path>/scripts/backup.sh`，
  不另拷 `/opt/<project>/backup.sh`。理由：单一真相——脚本随 repo 版本管理，
  避免「repo 内副本 + /opt 运行副本」双写漂移；repo 在家目录、重建不影响 /opt 数据卷与
  备份目录；T4.5 换版构建只动镜像，不动该路径。代价：repo 若被迁移/删除 cron 失效
  （由 36h 新鲜度检查兜底告警，见 §7 R-a）。脚本不依赖 cwd/相对路径（全部绝对缺省），
  cron 默认 PATH（/usr/bin:/bin）下实测通过（`env -i PATH=/usr/bin:/bin` 冒烟）。

## 4. 监控登记（运行侧，server-health-check.sh）

diff 摘要（全文 `t4.2-evidence/server-health-check.diff`；改前先 `cp` 至 `/tmp/t42-test/`，
sha256 before=`afa80ecf…` after=`7f754e68…`）：

```diff
 # 头部注释
-# …（磁盘/内存/服务/对端），异常时输出告警文本
+# …（磁盘/内存/服务/对端/备份新鲜度），异常时输出告警文本
 # 阈值区
+TENGU_DB=/opt/<project>/data/tengu.db        # 存在=已上线，才查备份新鲜度
+TENGU_BACKUP_DIR=/opt/backups/<project>      # T4.2 日备目录
+BACKUP_WARN_H=36      # 备份新鲜度阈值（小时）
 # 检查项 7（fail2ban 之后、输出段之前）
+# 7. tengu-bcdice-tg 备份新鲜度（仅当生产库存在=已上线时查；未上线不查=静默）
+if [ -f "$TENGU_DB" ]; then
+  LATEST_BACKUP=$(ls -1t "$TENGU_BACKUP_DIR"/tengu-*.db 2>/dev/null | head -1)
+  if [ -z "$LATEST_BACKUP" ]; then
+    ALERTS="${ALERTS}💀 tengu-bcdice-tg 库已存在但备份目录无任何 tengu-*.db（$TENGU_BACKUP_DIR）\n"
+  else
+    BACKUP_AGE_S=$(( $(date +%s) - $(stat -c %Y "$LATEST_BACKUP") ))
+    if [ "$BACKUP_AGE_S" -gt $(( BACKUP_WARN_H * 3600 )) ]; then
+      ALERTS="${ALERTS}⚠️ tengu-bcdice-tg 备份陈旧：最新备份 $(basename "$LATEST_BACKUP") 已 $(( BACKUP_AGE_S / 3600 ))h 未更新（阈值 ${BACKUP_WARN_H}h）\n"
+    fi
+  fi
+fi
```

- 语义：严格「超过 36h」= 秒级比较（`-gt 36*3600`）；取最新（mtime 序）`tengu-*.db`。
  未上线（DB 不存在）→ 整体跳过（静默）；库存活但零备份 → 也告警（见 §6 决策 5）。
- 纪律守住：脚本恒 `exit 0`（新检查只写 `ALERTS` 字符串，不影响退出码）；绿色路径零输出
  （M1/M2/M3b/M5 均零输出 exit 0）。
- 测试全程用 `sed` 管道副本 + `/tmp` 夹具换路径/阈值，**未为测试改动原脚本、未触碰真实
  `data/tengu.db` 与 `/opt/backups`**；运行验证只手动执行脚本（不经 主机 cron 投递）。
- 同步更新 skill `devops/server-lightweight-monitor`（检查项表 + 扩展方向）。

## 6. 实现级决策清单

1. **cron 直调 repo 路径**（非 /opt 拷贝）：单一真相，避免双写漂移（§2）。
2. **`.backup` 后加 `PRAGMA integrity_check` 自检**：小库毫秒级；坏副本当场暴露，
   失败即删半成品——否则坏文件 mtime 新鲜会骗过监控（假阴性风险反转）。
3. **保留清理只认严格形态 `tengu-[0-9]{8}.db`**：比 `tengu-*.db` 略宽于任务字面、
   略窄于 glob，确保「只动自己产出的文件」，手放的其他文件绝不误删（V3 已证）。
4. **脚本自带 `mkdir -p` + `chmod 700` 兜底**：目录被删后可自愈；/opt/backups 保持 root 不可写（最小放权）。
5. **「库存活但零备份」也告警**：任务只规定「超 36h」告警；零备份无法按 mtime 计时，
   按「从未更新（∞）」归入同一检查。理由：漏报「备份从未成功」将持续数周且静默，
   误报只在「上线首日 + 首备尚未发生」窗口出现一次且措辞明确。T4.5 缓解：上线当天
   手动跑一次 `scripts/backup.sh`（见 §7 R-d）。
6. **阈值/路径变量放脚本顶部同风格**：沿用既有 `DISK_WARN` 等直赋值风格；测试用 sed 换值，
   不为可测性引入 env 覆盖（监控脚本非本任务改造对象）。
7. **36h 阈值**：日备周期 24h 的 1.5 倍——容忍单次漏跑/机器晚开机的正常抖动，
   又能在一个备份周期内兜住连续失败。秒级 `-gt` 实现字面「超过 36 小时」。
8. ~~备份脚本同日重跑无锁：幂等语义（先删同名再备）已覆盖并发重复的最坏后果；
   不引入 flock 以免 cron 抖动时静默丢备份（宁可重叠一次）。~~
   **评审推翻（kimi T4.2 提案 #1）**：实测并发互删的最坏后果是当日零备份，
   「幂等覆盖」论断不成立。现态：flock 自互斥 + tmp+mv 原子顶替。
