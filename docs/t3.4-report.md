## 2. ct_command 15 文件逐条对照要点

总调度（`ctcommand.js`）：母本把整条命令内容**去掉全部空格**后按未转义 `,` 切分，

## 3. /ct 子命令映射表（主代理向用户呈报命名用）

全部 ASCII、空白分隔、`<角度括号>` 必填、`[方括号]` 可选。

| /ct 子命令 | 天狗对应 | 说明 |
|---|---|---|
| `create <表名>` | createTable | 建表（初始骰型 `a : 1d6`） |
| `rename <旧名> <新名> [t]` | updateTableName | 改名（t=公共表） |
| `dice set <表> <快捷名> <骰式> [t]` | updateDice | 骰式如 `1d6`/`2d6+3`/`3d6+x` |
| `dice del <表> <快捷名> [t]` | deleteDice | 快捷名 `a` 不可删 |
| `data set <表> <出目> [t] <结果文本>` | updateData | 文本可含空格；`t` 紧跟在出目号之后 |
| `data del <表> <出目> [t]` | deleteData | 出目必须是半角数字 |
| `range <表> <最小> <最大> [t]` / `range <表> off [t]` | （母本无命令层入口） | 显式开关范围钳（登记为超越母本项） |
| `perm add <表> <用户ID> [t]` | addPermission | 用户 ID = Telegram 数字 ID |
| `perm del <表> <用户ID> [t]` | deletePermission | 前三位（管理位）不可删 |
| `publish <表>` | publishTable | 发布为公共表（是「移」不是复制） |
| `delete <表> [t]` | deleteTable | 删表 |
| `show <表> [t]` | checkTableData | 表详情（骰型/范围钳/权限/数据） |
| `list` | checkTableList | 本群表 + 公共表一览 |
| `roll <表> [快捷名] [補正]` | SearchTableDiceroll | 掷表；查找顺序 内置→本群→公共 |
| `help [子命令]` | help | 总用法 / 分题帮助 |

**flag 位置规则**（`t/T`=公共、`f/F`=本群；其它 → 报错）：定长命令在**末位**；
`data set` 因尾部是自由文本，flag 在**出目号之后紧邻位置**（如 `/ct data set T 3 t 文本`）。
解析全部**按位置**，不做内容猜测。

## 4. 实现级决策清单

1. **表名规则适配**：母本 `checkInvalidChar` 禁「ASCII 字母数字 + `#[]()'`" ,.\/` + 空白」
   并要求「全角 4 字以上」——那是为「日文表名直打」（表名即掷骰触发词）设计的。
   本项目表名只作为 `/ct` 参数出现，且**内置表名是 ASCII**（SBX/KRS/NSRS…）；若沿
   母本禁 ASCII，则「内置表撞名」检查**永远不可触发**（验收钉要求两路可拦），故改编为：
   **非空、无空白/控制字符、长度 1..32**（CJK/ASCII 均可）。判据集中在 `valid_table_name?`。
2. **分隔符改空白**：母本去空格 + 逗号分割 + `\,` 转义——本项目不搬转义层
   （Telegram 输入习惯），副作用：数据文本可以含空格（对用户是增强）；
   表名/快捷名因 token 化天然不含空白（与母本一致）。
3. **超钳的处理**：天狗语义 = **取端点**（`NJDiscordReply.js:91-95`，其 help 亦原文
   「結果に応じてデータ範囲の最大値or最小値を表示します」）。本项目照搬取端点，
   并按 T1.4 已立的「钳制发生时明示」约定输出标注
   `（出目 14 超出钳制范围 1..6，按钳制取 6）`。
   **验收词「超钳报错」的落点即此**：超钳必须显式报给用户（绝不静默），但**不拒绝掷骰**
   （拒绝会偏离母本语义）。若评审要求硬拒，改动点集中于 `sub_roll` 的钳制分支一处。
4. **群管理员旁路的范围**：旁路（Admin#admin?）**只对本群私有表生效**。公共行
   （scope=public）没有「本群」，若让任意群管理员可改公共表，等于把全服公共表编辑权
   发给每个群的管理员（且公共行连 getChatMember 都不查，省一次 API）。母本对公共行
   同样只认表自身的权限数组。
5. **show 的内置指路**：`show 名字` 未命中 DB 但是内置表时，回「是内置表…/ct roll 或
   /nd」——撞名阴影的 UX 补丁（超越母本的小提示，登记）。
6. **dataVerification 两处口径**：① 母本算式累计有 JS 字符串拼接 quirk
   （常量项逐字拼成字符串，`1d6+5` 会算出 `"15"`），本实现按**整数语义**；② 除了母本
   的 isUse 跳过，**骰式含 `+x` 也跳过**（母本 help 原文「判定できないため…スキップ」；
   正常流程下二者等价，因为 updateDice 会在出现 +x 时自动开钳——差异只在手动 `range off`）。
7. **publish 补权限检查**：母本代码**无**检查（help 承诺「bot管理者/サーバー管理者/
   テーブル作成者」）；本项目按计划 §5 与 help 承诺落到**前三位**判据。属超越母本的补检查。
8. **切段归发送层**：母本 `checkTableData` 的 1900 字手工切段是 Discord 侧产物；
   本项目 handler 只回一个字符串，由 TelegramApi 的 Chunker 按 4096 切段（同 dice.rb 纪律）。
9. **`range` 命令 = 新增**：母本钳制纯由 dice/data 编辑自动维护、无命令层入口；
   为把 T3.3 的 `set_datarange`（12 操作之「改范围钳」）暴露到聊天层而新增。
   自动维护会**覆盖**手动 range（母本语义：范围由 data 键域推导），已登记。
10. **内置桥排除 SPIKE_DUMMY**：T1.1 spike 的占位表（未注册命令、不可触发）不是真正的
    内置表；排除对「撞名检查」与「查找顺序」**同时**生效（两者读同一 map，不会错位）。
    保留 23 张 = `i18n_key_ledger.yml` 的已映射计数。
11. **`EMPTY_TEXT` 防御分支**：`data set T 3 t 文本` 的 t 被视作 flag 后若没写文本 →
    报「结果文本为空」。token 化下正常输入几乎不可达，保留为防御（同 bank 的
    `attempted` 分支先例）。
12. **補正值口径微差**：母本 `Number()` 接受 `1e5`/`0x10` 这类形态；本项目只收
    `[+-]?\d+(\.\d+)?`（+floor）。垃圾输入上的未申报……**实为申报**：`1e5`/`0x10` 按
    非数字**忽略**（母本对非数字的语义即忽略，此处只是判定集略窄）。

## 5. 权限模型落点（母本逐操作 + Telegram 化）

| 操作 | 母本判据 | 本项目（`write_allowed?` 的 rule） | 群管理员旁路 |
|---|---|---|---|
| create | 无（人人可建） | 无 | — |
| rename | permission[0..2] | `:admin_bits` | ✅（私有行） |
| dice set / dice del | **全体** permission | `:permitted` | ✅ |
| data set / data del | **全体** permission | `:permitted` | ✅ |
| range（新增） | —（母本无此命令） | `:permitted`（与骰型/数据同族） | ✅ |
| perm add / perm del | permission[0..2] | `:admin_bits` | ✅ |
| publish | 母本**代码无检查**（help 承诺三档） | `:admin_bits`（补检查，决策 7） | ✅ |
| delete（私有行） | permission[0..2] | `:admin_bits` | ✅ |
| delete（**公共行 t**） | **只认 permission[0]** | `:first_permission`（无旁路） | ❌（决策 4） |
| show / list / roll | 无（读操作） | 无 | — |

- 文案分三档（对应母本三条固定句）：「你没有操作表「X」的权限…」/「只允许表权限前三位
  （管理位）…」/「公共表只能由该表的第一位权限用户删除。」。
- 「不许删前三位」在 handler 拦（母本 deletePermission.js:17-20）；db 层 `set_permissions`
  是整体替换、不内置该限制（T3.3 既定纪律）。

## 6. 内置表桥（BuiltinTables）设计

- **数据源**：`I18n.t("NinjaSlayer2Ex.table")` + `I18n.t("NinjaSlayerEx.table")`
  （`i18n/*/ja_jp.yml`，T1.2 管线自 nd_datatable.js 机器生成；须先
  `EngineBootstrap.bootstrap!`）。实测要点：**I18n 返回 Symbol 键的 Hash**（取值两态兼容）；
  namespace 缺失 → `raise: true` 捕获后按空表 + 结构性 warn（不抛、不静默全量补丁）；
  排除 `SPIKE_DUMMY`（决策 10）。
- **形状**：`{ downcase 表名 => BuiltinTables::Table }`；`Table` 提供与 `CustomTable`
  同形的读取面 `dice_string(kind)` / `data_entry(index)` / `datarange`（= unbounded，
  内置表在 `/ct roll` 路径不带钳制）。
  - `dice` = `{"a" => yml type的小写}`（yml type 即**默认骰型 a**；多骰型 a~d 与 `+x`
    補正走引擎命令，不经此桥）；
  - `data` 键偏移 = **默认骰型的最小出目**：`1d6→1`、`1d36→1`、`2d6→2`
    （CYBER/SUMMON 是 11 条 2..12，与 ledger 的 min/max_index 一致），值 = items 逐字。
- **两种形态**：`map`（Hash）/ `source`（callable，供 `resolve_table(builtin:)`）/
  `names`；撞名检查与查找顺序读**同一张 map**。懒构建 + 缓存，`reset!` 供测试。
- **失效方向**：读取异常/未 bootstrap → 空表 + warn → 「查不到内置表」与「撞名检查
  查不到」**同向失败**（fail-open 对称：不会出现「拦住却查不到/放行却掷不出」的错位）。
- **接缝图**：`/ct roll` → `CustomTables#resolve_table(builtin: BuiltinTables.source)`
  → 命中 → handler 用 `Table#dice_string/data_entry` 掷表；`create`/`publish` →
  `builtin_table?` 用同一 source 查名。db 层零引擎依赖（T3.3 契约不变）。
- **边界**：`/ct roll <内置表>` 只按默认骰型 a 掷（如上）；想要 a~d/`+x` 全语义时用引擎
  原生命令（如 `/nd KRS_C@2`）。遗留见 §8-3。

## 8. 遗留风险

1. **改名可造出「被内置阴影」的名字**（母本忠实：updateTableName.js 不查内置表）。
   用户把自建表改成 `SBX` 后，掷表查找会命中内置表而非它。已在测试里钉住该行为；
   若要补检查属超越母本，建议由主代理拍板后再做（改动点：`sub_rename` 一处 + 文案）。
2. **公共行的群管理员盲区**：公共表只能由表自身权限者（删除时限 permission[0]）维护，
   原群管理员撤不服。这是决策 4 的代价（安全侧）；若日后要开「发布群管理员可维护」，
   需在行上保留来源群（schema 变更）。
3. **内置表在 /ct roll 只支持默认骰型 a**（见 §6 边界）：`krs` 的 b/c/d/`+x` 不在桥里。
   若日后要全骰型，可从 `references/extracted/i18n_key_ledger.yml` 的 `dice_ranges`
   （nd_datatable.js 的机器镜像）扩展桥——本次按任务书「读引擎侧 i18n」只做 yml。
4. **`range` 命令被后续自动维护覆盖**（决策 9，母本语义）。用户视角的「我设的范围怎么
   变了」需要文案引导；当前 `/ct help range` 已注明「数据录入会自动维护范围」。
5. **flag 位置习惯**：`data set` 的 flag 在出目号后（自由文本之前）——与微信/一般 CLI
   习惯略有不同；文本恰好带前导 `t ` token 时会被当 flag（位置解析不做内容猜测，
   已文档化并测试）。上报用户时请在说明里点出。
6. **`(chat_id, thread_id)` 无关**：CT 表按天狗原义是频道级 → 本项目群级（forum 内所有
   话题共享），roll/show/list 都不分话题（T3.3 报告 §6.3 的既定取舍，非缺陷）。
7. **观察项**：`show` 明细单条可能超 4096（大表）→ 由 Chunker 切段（多条消息无「续」标头，
   与引擎输出同一观感）；`list` 同理。
