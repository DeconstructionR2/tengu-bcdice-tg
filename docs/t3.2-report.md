## 1. record.js 逐行对照要点

### 1.1 操作集与入口（record.js:14-43 `receiveResponce`）

天狗的 `/tb <操作>` 由 `discord_command/tb.js` 把 option **原样透传**给 `receiveResponce`
（tb.js 只做 `editReply("/tb " + option + "\n" + reply)` 的回显包装，无任何语义）。
操作集全部来自 record.js 的 switch，共 6 个 case + default：

| record.js case | 目标函数 | 本项目子命令 |
|---|---|---|
| `m` | `recordMoney`（:78） | `deposit` / `withdraw` |
| `i` | `recordItem`（:94） | `item add` / `item del` |
| `reset`、`delete` | `deleteRecord`（:113） | `reset` |
| `result`、`end` | `getRecordResult`（:118） | `statement` |
| `check` | `getRecord`（:152） | `balance` |
| default | `error.replyErrorMessage()` | 输入错误 |

### 1.2 请求切分（record.js:45-70 `splitRequest`）

```js
const M_PLUSNUMBER = /^m\+\d+$/;
const M_MINUSNUMBER = /^m-\d+$/;
const I_PLUSITEM   = /^i\+.+$/;
const I_MINUSITEM  = /^i-.+$/;
```

四个关键事实，逐条落地：

1. **`\s+` 全量剥离**（:15 `content.replace(/\s+/g, "")`）→ 本项目等价做法：按空白切词，
   动词与参数分离；道具名可含空格（天狗的 `i+.+` 同样允许）。
2. **金额只收无符号纯数字**：`m+N` / `m-N` 里 `+`/`-` 是**操作符**、不是金额的符号。
   故 `deposit -50` 在天狗那里两条正则都不匹配 → 落 default → 输入错误。
   本项目符号**只由动词决定**（`parse_amount` 只收 `\d+`）。
3. **道具名过 Markdown 转义**（:58/:64 `escapingMarkDown`，转义 `* _ ~ | \` >`）：
   那是因为 Discord 会把未转义记号当格式渲染。**本项目不转义**——§13 第 7 项
   第一版纯文本、不带 `parse_mode`，转义反而会把 `\` 显示出来。
4. **`parseInt` 后进 `saveRecord`**：`m+100abc` 在天狗是正则不匹配（不是 parseInt 容错），
   故本项目整体串匹配 `\A\d+\z`，不做「取前缀数字」的宽松化。

### 1.3 `recordMoney` / `recordItem` 的两态回显（:78-111）

```js
if (!array[1]) return error.replyErrorMessage();   // 0 与空都算 falsy → 输入错误
const result = await TB.TB.saveRecord({...}).catch(() => null);
return result == null ? error.replyErrorMessage() : "万札を更新しました。…";
```

- **`0` 被 falsy 拦掉**：本项目 `amount.zero? → BAD_INPUT`，已钉测试。
- **`saveRecord` 回 null 有两个来源**：道具不在账上（`checkRecSplit` 判 false）与
  写入失败。本项目用 `SaveResult` 三态（`:ok` / `:item_missing` / `:error`）区分，
  前者给天狗专句「そのアイテムの記録はありません。」，后者给输入错误。
- **`recordItem` 的 `if (!result)` 先于 `result == null`**（:103）：两者都真，
  但前者还会吞掉空串/0 之类。本项目统一走 `result.ok?` 分支，语义等价。

### 1.4 `getRecord` / `getRecordResult` 的区别（:118-178）

- **两者出的是同一段报表**，唯一区别：`getRecordResult` 结尾多一个
  `await TB.TB.delete(channelID)` 并把 delete 的返回串**追加**到输出末尾。
- 天狗的 DELETE 失败会把**整条**输出换成错误文案（:146 `returnString = error...`）。
  本项目在 handler 里同款分支（注入假 bank 可达，见 §4 测试清单）。
- **查无此账的早退文案**：「このチャンネル内の記録が見つかりません。」，
  且 `getRecordResult` 此时**连 DELETE 都不发**（:122 直接 return）→ 本项目
  `statement` 返回 `[nil, false, false]`，handler 回「没有找到银行的记录。」且不追加重置句。

### 1.5 流水字符串 → 算式（:124-127 / :158-161）

```js
money_record.replace(/、/g, " + ").replace(/\s\+\s-/g, " - ")
```

本项目把该字符串拼装**还原**到 `BankRecord#money_flow_text`（`[100,-50]` → `"100 - 50"`），
落库形态则是 JSON 数组（§4.1 定案）。两处观感一致，见 §3。

### 1.6 `change893`（:180-185）

```js
if (String(money).indexOf("893") !== -1) money = ":japanese_goblin:  " + money + "  :japanese_goblin:";
```

判的是**字符串包含**、不是数值等于 893：余额 1893 / 8930 / **-893** 全命中。
本项目保留 `include?("893")` 语义；装饰字符由 `:japanese_goblin:` 换成 Unicode
**👺**（Discord 自定义 emoji 语法在 Telegram 不会被渲染成图案，纯文本 Unicode 才保真）。

### 1.7 tb_db_wrapper.js 的 saveRecord（:11-53）

- **无数据 → 无条件建档**（:13-22）：`sum_money = money`、`money_record = String(money)`、
  `item_record = item ? String(item) : ""`。⚠️ 这一行**不看 `isItemAdd`** ——
  空账上「取道具 茶」会建出一个 `item_record = "茶"` 的账（取走反而多一件）。
  本项目忠实保留并用测试钉死（`test_first_write_that_is_only_a_delete_still_opens_an_empty_ledger`）。
  同理首次只存道具时 `money_record` 是 `[0]`（天狗 `String(0)` = `"0"`）。
- **追加分支**（:24-28）：`sum += money`；`if (money != 0)` 才追加流水。
- **删除分支**（:32-38）：见 §3 ②。
- **`:45` 之后的分隔符修补三连**（首尾去 `、`、连续 `、、` 合并）在 JSON 化后**结构性消失**
  ——数组没有分隔符，这正是 §4.1 定案 JSON 化的收益之一。

## 2. 子命令映射表（交付给主代理呈报命名）

纯 ASCII（§13 第 2 项），全部与 record.js 操作一一对应：

| /bank 子命令 | 天狗写法 | record.js 操作 | 语义 | 是否动账 |
|---|---|---|---|---|
| `/bank deposit <金额>` | `m+100` | `m` → `recordMoney` | 存钱 | 是 |
| `/bank withdraw <金额>` | `m-50` | `m` → `recordMoney` | 取钱（**可透支**） | 是 |
| `/bank item add <道具名>` | `i+茶` | `i` → `recordItem(isItemAdd=true)` | 存道具 | 是 |
| `/bank item del <道具名>` | `i-茶` | `i` → `recordItem(isItemAdd=false)` | 取出道具 | 是 |
| `/bank balance` | `check` | `check` → `getRecord` | 查账（余额+道具+流水算式） | **否** |
| `/bank statement` | `result` / `end` | `result` → `getRecordResult` | 出结算后**清零** | 是（清零） |
| `/bank reset` | `reset` / `delete` | `reset` → `deleteRecord` | 清空本话题的账 | 是（清零） |
| `/bank help` | （天狗无） | — | 用法表 | 否 |
| （无参 `/bank`） | （天狗无） | — | 用法表 | 否 |

**有意不搬的三个别名**（实现级决策，非遗漏）：

- 天狗 `delete` ≡ `reset`、`end` ≡ `result`：同义别名在纯 ASCII 命令表里是维护负担
  （改一处忘另一处），且 Telegram 菜单只有一条 `/bank` 描述。
- 天狗道具名的 Markdown 转义（`escapingMarkDown`）：本项目纯文本模式，转义会露出反斜杠。

**动词大小写不敏感**（`DEPOSIT` = `deposit`），Telegram 用户输入法大小写不可控。

## 3. 流水 JSON 化与 quirk 修复的语义差异说明

### ① 流水：字符串 → JSON 数组（§4.1 定案）

| | 天狗 | 本项目 |
|---|---|---|
| 落库 | `"100、250、-50"`（`、` 分隔） | `[100,250,-50]` |
| 首次建档 | `String(money)` = `"0"` / `"100"` | `[0]` / `[100]` |
| 展示 | 出库时 `replace` 拼算式 | `BankRecord#money_flow_text` 还原同一算式 |
| 断言粒度 | 只能整串比对 | 逐元素：`[100,250,-50]` |

收益：可断言到元素级（流水测试逐条钉）、可程序化按笔统计；代价：无（展示层已等价还原）。
**空账差异**：天狗 `money_record` 是空串（falsy → 不显示算式行），本项目是 `[]`
（`money_flow_text` 回 nil → 同样不显示）。**行为一致**。

### ② 删道具：字符串 replace → 元素级删除（quirk 修复，§4.1 注记）

天狗 tb_db_wrapper.js:38：

```js
data.item_record = String(data.item_record).replace(item, '');   // 删首个「子串」
```

它与上方 `checkRecSplit`（判**完全相等**）的判据**不一致**，导致两类错删：

| 账上道具 | 删除 | 天狗结果 | 本项目结果 |
|---|---|---|---|
| `ポット改、ポット` | `ポット` | checkRecSplit 命中 → replace 削掉「ポッ**ト**改」的「ト」→ 账变 `改、ポット` | 只摘掉完全相等的 `ポット` → 账为 `ポット改` |
| `ポット改`（仅此一件） | `ポット` | checkRecSplit 判 false → 回 null → 「そのアイテムの記録はありません。」 | 同（`item_missing`），且不碰 `ポット改` |

两条都用测试钉死（`test_removing_an_item_is_element_wise_not_substring` /
`test_removing_a_prefix_only_item_is_refused_not_silently_mangled`）。
天狗的分隔符修补三连（首尾去 `、`、`、、` 合并）在数组模型下**结构性不存在**。

### ③ 金额上限：int64 校验（**本项目新增，非天狗行为**）

SQLite 的 `INTEGER` 列是**动态类型**：实测超 int64 的值会被**静默存成 REAL**
（`10**25` → `1.0e+25`）。天狗后端 Firestore 的整数字段会**拒绝**写超界值 →
`saveRecord` 抛错 → `.catch(() => null)` → 玩家看到输入错误。

若不校验：REAL 会污染 `sum_money`，此后每次累加都变成浮点运算、
`money_record` 里混入浮点、且 `change893` 的字符串判定失真。
故本文件显式校验并回 `:error`（用户看到「输入有误」，与天狗**同一文案**）。
校验点放在**累加之后**（`sum` 才是真正落库的值）。

### ④ 忠实保留（含「看起来像 bug 的部分」）

- **无透支校验**：余额可为负（`withdraw 9999` 余额 100 → `-9899`）。
- **`0` 输入被拒**：JS falsy，非本项目额外校验。
- **空账上「取道具」反而建出并记入该道具**（:1.7 的 `isItemAdd` 盲区）。
- **道具名不去重**：同名存两次 = 账上两件；删一次只摘一件。
- **清零对空账也报成功**（Firestore 删不存在的文档不报错）。
- **结算查无此账时不执行清零**。

### 作用域：话题级（§13 第 8 项）

天狗 `collection 'tengu-bank'` 是**每 Discord 频道一份文档**；本项目映射为
`(chat_id, thread_id)` 复合键——forum 群的话题 ≈ Discord 频道，forum 外的
普通群/超级群 ≈ 群级 `thread_id=0`。thread 归一**复用** `db/settings.rb` 的
`normalize_thread_id`（E4：`nil/0/1/负数 → 0`），本文件不另抄一份。

## 5. 实现级决策清单

| # | 决策 | 理由 |
|---|---|---|
| 1 | `SaveResult` 三态返回而非抛异常 | 天狗用 `null` 表达「道具没有/写失败」，handler 必须区分文案；异常会让 router 兜底吞掉用户应答 |
| 2 | 归一只实现于 `db/settings.rb`，`Bank.normalize_thread_id` 转发 | 两处抄本必然漂移（router.rb 对命令集合的同款纪律） |
| 3 | 整行读改写走 `:immediate` 事务，且**块内绝不 return** | sqlite3 的 `transaction` 在块内 `return` 时走 ensure 的 **commit**，半截改动会被提交 |
| 4 | int64 显式校验（累加后） | SQLite 动态类型会静默存 REAL（§3 ③） |
| 5 | `chat_id == 0` 拒绝 | Ruby 里 0 为真，不拦会写进 chat_id=0 黑洞（与 migration 的 0 守卫同款） |
| 6 | JSON 列解析失败降级为空数组 + warn | 人工灌库/旧版本写坏时，用户要看到余额而非「bot 报错」 |
| 7 | handler **返回 String 由 router 代发**（非 T3.1 的恒 nil） | 银行是公开账本，结果本就该全群可见；无「绝不经代发」的命门 |
| 8 | 发送封装全部走 router 代发 + thread 透传 | T3.1 纪律；handler 不自己调 api，故不涉及 `thread_id 0→nil` 那个坑 |
| 9 | 893 装饰用 👺 而非 `:japanese_goblin:` | Discord 自定义 emoji 语法在 Telegram 不渲染；§13 第 7 项纯文本 |
| 10 | 道具名不做 Markdown 转义 | 纯文本模式，转义会露出反斜杠 |
| 11 | 不加天狗的同义别名（delete/end） | 见 §2 |
| 12 | `/bank` 从 PendingHandler 换成真 handler，`/help` 同步补条目 | T2.6 教训：菜单上架命令必须有真应答，且帮助文案不得陈旧 |

## 6. 遗留风险

1. **未做真机验收**（全部为 mock 单测）。需在测试群真机跑一遍
   「存钱→存道具→查账→结算→清零」并确认话题级隔离与彩蛋观感。
2. **流水无上限**：`money_record` 随每笔非零出入金增长，长跑团群可能积累到
   数千条；`/bank balance` 会把它整行拼出来（发送层按 4096 字符切段，观感变差）。
   天狗有同样问题（字符串无限增长），故本任务未加限流；如需，属 backlog。
3. **`statement` 的失败分支在真 DB 下不可达**（DB 层抛异常走 router 兜底），
   目前由注入假 bank 的测试保活。若日后 DB 层改为返回 false 表达故障，该分支即生效。
4. **`change893` 判的是余额串含 "893"**（天狗原样），故余额 1893/8930/-893 都会
   被小怪包住——这是彩蛋不是 bug，但首次遇到的用户可能困惑，帮助文本未逐条解释。
5. **余额为负时 `893` 判定对 `-893` 成立**（同第 4 条，天狗一致）。
6. **群升级 re-key** 由 T2.5 的 `Migration::TABLES` 覆盖 `bank_record`，
   已补迁移联动测试；但**真机群升级**路径未验（依赖测试群真的再升一次）。
7. **`/ct` 与 `/log` 仍是 PendingHandler 占位**（T3.3/T3.5 提供），
   `/bank` 已从占位名单移出，帮助文本同步更新。
