## 2. 关键决策

### D1 — E4 落地：`thread_id ∈ {0, 1}` 归一为群级

§15.3 E4 的原文问题：forum 群所有消息都带 `message_thread_id`，General 话题恒为 1，于是「话题外打 = 群默认」在 forum 群内**没有对应场景**。归一规则（`Settings.normalize_thread_id`）：

```
nil / 0 / 1 / 负数  → 0（群级）
> 1                → 原值（话题级）
```

**读写都必须过这一层**——否则 General 里写的行落在 `thread_id=1`，普通群查 `thread_id=0`，两者互相看不见。5 条用例钉死这个对称性（`test_general_topic_write_visible_outside` 等）。

### D2 — slash 提示 vs 辅助轨静默（不对称是有意的）

slash 是**显式意图**（用户打了 `/roll`），引擎 nil 时回一句「该规则系统不接受这个命令」是正当反馈；辅助轨是**bot 自己猜**这行是骰式，回一句等于公开抢话。router 的闸门是**语法闸**（t2.3 D2），`NRS` 这类语法合法、引擎 nil 的输入本就会被放行——若辅助轨也提示，`NRS` 会让 bot 逢群必言。**故 aux 轨 nil 一律静默**（含「设置指向不存在的规则系统」这一分支）。

### D3 — DB 层不碰引擎，引擎校验在 bot 层

`db/settings.rb` 不 require BCDice、不校验规则系统 ID 是否存在；`dice.rb` 的 `EngineResolver` 才做 `BCDice.game_system_class` 校验。理由：① DB 层单测因此不必 bootstrap 引擎（快，且不与引擎初始化顺序耦合）；② 「ID 有效性」是引擎域的知识。

代价：设置里可能存入无效 ID（手改 DB / 换 gem 版本）。**不静默崩**——slash 轨回「规则系统 X 当前不可用（可能已被移除）」，aux 轨静默（2 条用例）。

### D4 — 启动期强制开库（部署故障早暴露）

原本 settings 是惰性打开的（首次掷骰才建库）。但 `DB_PATH` 写错 / 数据卷没挂是**部署期**故障——若等到群里第一条消息才炸，玩家看到的是「bot 装上了但一直不掷骰」，排查成本高一个数量级。故 main.rb 在起长轮询前 `dice.settings` 一次，失败即 `exit 1` 并给出「核对 DB_PATH 与数据卷权限」的提示（与既有「菜单注册失败就 exit 1」同一条纪律）。子进程冒烟用例 `test_startup_registers_dice_handlers_and_uses_db_path` 正是为这条而写。

### D5 — 两处 sqlite3 gem API 陷阱（实施期实测踩到，已留注释）

1. **`results_as_hash` 是连接级全局状态**：用 `get_first_row` 拿 Hash 行必须先开它，而开完不还原会**串味**后续用例（拿到数组行 → `row["game_system"]` TypeError，报错点离病根很远）。故 `Connection#get_first_hash` 显式 save/restore，不改全局模式。
2. **`execute` 返回的是结果集，不是 change count**：`DELETE` 一律返回 `[]`，拿它判「删没删掉」会永远 false。故 `Settings#delete` 读 `Connection#changes`。

### D6 — 事务嵌套用「复用外层」而非 savepoint

sqlite3 gem 明确不支持嵌套（抛 `cannot start a transaction within a transaction`）。`Connection#transaction` 检测到已在事务中就**直接 yield**——内层复用外层，外层失败整体回滚。语义正确（savepoint 之外的做法），且避免给每张表开 savepoint 的额外 IO。

### D7 — 索引只建一条，并写明理由

`chat_settings`/`bank_record` 的主键 `(chat_id, thread_id)` 前缀已覆盖唯一热路径（按群/话题查），再建索引是纯写放大；`secrets` 的按 chat 清理与 `session_logs` 的按群列举都是低频，等 T3.x 有实测访问模式再定。**理由写在 schema.sql 里**，避免后人「补齐索引」时看不出这是有意取舍。

### D8 — 超长输出：handler 不截断，发送层切段

handler 只交字符串（不预切、不截断），4096 切段是 `TelegramApi::Chunker` 的既有职责（t2.1）。新增端到端用例用假引擎造 8000 字符输出，断言：切成多段、每段都带 `message_thread_id`、**拼回去逐字一致**。

### D9 — `/system` 的 ID 校验按大小写敏感

`BCDice.game_system_class` 是**精确匹配**（`NinjaSlayer2Ex` / `ShinobiGami` 等）。实测 338 个 ID **无大小写冲突**（`ids.group_by(&:downcase)` 无碰撞组），故不做大小写归一——归一反而会让用户输入的 ID 与落库的 ID 不一致。真实 ID 大小写错配的常见形态是下划线 vs 冒号（`Alsetto` vs `Alsetto:Korean`），**两者都是合法独立规则系统**，任何自动纠正都是错的。

### 4.3 main.rb：子进程跑真启动路径

main.rb 是**入口脚本**（加载即启动长轮询，不可 require）。本任务用「子进程 + `prepend` 假传输层」跑真实启动路径：

- **为什么 prepend 而不是换常量**：main.rb 调 `TelegramBot::TelegramApi.commands_payload`（类方法）。换掉常量等于把整个类抽走，测的是替身；prepend 只覆盖 `initialize`/`start` 两处会联网的点，**MainMenu、Chunker、Router、handlers、DB 全是真代码**。
- 实际验证：`DB_PATH` 生效并建库 → schema 落地（`chat_settings` 在）→ 主轨菜单注册 → 喂 4 条 update（`/roll SB`、裸 `SB`、`/system NinjaSlayerEx`、`/help`）→ 断言发 **3** 条、`/help` 静默、topic 88 逐条透传、**(chat_id, 88) 行真落库为 `NinjaSlayerEx`**、启动日志不含 token 值。
- 假 token 用 `"1234567890:FakeTokenForUnitTests0000"`（形状合法以过 `Config` 校验，**非真 token**），并用 `refute_includes` 断言它没出现在任何日志里。
