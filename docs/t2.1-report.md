## 2. 关键决策

### D1 — bootstrap 双模式（`reload_backend:`）

默认 `false`：仅首次调用执行 `reload!`，后续空转（生产长驻进程不在热路径反复全量重载 105+ 个 yml）。测试与一次性脚本传 `reload_backend: true` 强制每次重载。

`inject_i18n_load_path` 返回**本次新增条目数**，使"幂等"可被断言而不是靠肉眼看 load_path 长度。

### D2 — 注入用 `concat(new - existing)` 而非 `<<`

`I18n.load_path << Dir[...]` 会塞进一个 **Array 元素**（spike 报告坑点 B），靠 i18n 的 `filenames.flatten.each` 兜底。本仓库一律 `concat` 平展。

> **实证发现**：上游 bcdice **自己就用了 `<< Dir[...]`**——`bcdice-3.17.0/lib/bcdice/base.rb:414`。实测 `I18n.load_path` 里天然存在 1 个长度 105 的数组元素。故守卫不能断言"整个 load_path 无数组元素"，只能断言**本仓库的 yml 是扁平 String 条目**（已按此写测试并留档）。

### D3 — `send_one` 按 `chat_id/thread_id` 维度配速

Telegram 限流是「每聊天 1 条/秒」（§0.2.4）。forum 群下按 `chat_id/thread_id` 组合键计数，话题间互不阻塞。时钟与 sleeper 均注入，测试零真实等待。

### D4 — 切段按字符不按字节

Telegram 上限是 4096 **字符**（UTF-8 码点）。日文表文本一字符 3 字节，按字节切会切得过碎；用 `byteslice` 切还会切坏多字节字符产生乱码。实现按 `each_line` 逐行累积（优先行边界），超长行退回 `each_char` 硬切，**全程不用 `byteslice`/`sub`**。测试以 `assert_equal 4096*3, segs.first.bytesize` 钉死"按字符计"。

### D5 — 保留 raw_api_call 作为保底通道，不依赖 gem 透传结论

§3 的实测结论比计划 R2 的预期**乐观**（gem 其实不校验参数），但实现**不**依赖该结论：`send_one` 与 `register_main_commands` 都对 `NoMethodError` 做降级到 `raw_api_call`。这样即使将来 gem 换成严格校验或升级后行为变化，主路径也不会断。

### D6 — 两个测试框架必须分 rake 任务

**踩坑记录**：最初把 bot 层（minitest）加进 `:default` 的同一 `test_files`，结果 773 条 test-unit 测试**全部消失**、只跑出 66 条 minitest，且**退出码仍为 0**——极易误判为全绿。根因：minitest 的 autorun 在 `at_exit` 里跑完即 `exit`，test-unit 的 `at_exit` 根本没机会执行。现拆为 `:default`（引擎层）与 `:bot`（bot 层），`rake verify` 连跑两者。

## 3. gem 白名单端点静态核查证据（供 T2.2 spike 参考）

**核查对象**：`vendor/bundle/ruby/3.2.0/gems/telegram-bot-ruby-2.8.1`（VERSION 见 `lib/telegram/bot/version.rb`：`'2.8.1'`）。

### 3.1 白名单只约束**方法名**，不校验**参数**

`lib/telegram/bot/api.rb:24-35`：

```ruby
def method_missing(method_name, *args, &block)
  endpoint = method_name.to_s
  endpoint = camelize(endpoint) if endpoint.include?('_')
  return super unless ENDPOINTS.key?(endpoint)   # ← 只查方法名
  result = call(endpoint, *args)
  ...
end
```

`lib/telegram/bot/api.rb:44-51`：

```ruby
def call(endpoint, raw_params = {})
  params = build_params(raw_params)   # ← 仅对 Hash/Array 做 to_json，无 schema 校验
  path = build_path(endpoint)
  response = connection.post(path, params)
  ...
end
```

**推论**：未收录的**方法名** → `NoMethodError`；未收录的**参数** → 照原样 POST 到 wire。

### 3.2 `setMyCommands` 在白名单内，`is_ephemeral` 是合法字段

- `lib/telegram/bot/api/endpoints.rb:96`：`'setMyCommands' => Types::Bool,`
- `lib/telegram/bot/types/bot_command.rb:9`：`attribute? :is_ephemeral, Types::Bool`

### 3.3 缺失的响应侧类型（+ 更正）

- ~~`grep -c ephemeral lib/telegram/bot/api/endpoints.rb` → 0~~ **更正（T2.1-review F9）**：实测为 **5** 条——endpoints.rb:149-157 已收录 `editEphemeralMessageText` / `editEphemeralMessageMedia` / `editEphemeralMessageCaption` / `editEphemeralMessageReplyMarkup` / `deleteEphemeralMessage`（gem 2.8.1 原生支持 ephemeral 管理端点）。正面含义：T3.1 暗骰的 gem 通路（含编辑/删除 ephemeral 消息）预期可行，T2.2 spike 仅剩服务端验证。
- `Telegram::Bot::Types.const_defined?(:EphemeralMessageParameters)` → **false**（响应侧类型仍缺，但只要不依赖该类型的结构化解析，无影响）
- 但 `Message#ephemeral_message_id` **存在**（`types/message.rb:16`）

### 3.4 离线实证（桩掉 Faraday，记录实际 POST，未联网）

| 场景 | 结果 |
|---|---|
| 未知端点名 `api.notAMethodInTheWhitelist` | `NoMethodError` ✅ 白名单生效 |
| `set_my_commands(commands: [...BotCommand(is_ephemeral: true)])` | 返回 `true`，**无 ArgumentError** |
| 实际 POST body | `[{"command":"start","description":"开始"},{"command":"secret","description":"暗骰","is_ephemeral":true}]` |
| `is_ephemeral` 是否到达 wire | **true** ✅ |
| `send_message(..., ephemeral_message_parameters: {receiver_user_id: 42})` | 无异常，参数 JSON 化后透传 ✅ |

### 3.5 与计划 §12 R2 的偏差（**重要**）

计划 R2 原假设：「gem 为白名单端点、未收录新参数大概率直接 ArgumentError，HTTParty 直调按正式方案对待」。

**实测与该假设部分相反**：`ArgumentError` 的风险不存在——gem 对参数**完全不做校验**。真实约束只有两条：

1. **方法名**必须在 `ENDPOINTS` 白名单里（新端点会 `NoMethodError`）；
2. **响应侧类型**缺失（`EphemeralMessageParameters` 不存在）——但只要不依赖该类型的结构化解析，无影响。

**结论**：T2.1 的 `setMyCommands + is_ephemeral` **走 gem 原生路径即可**，不必经 raw 通道；`raw_api_call` 保留为新端点的保底通道（这是真实存在的风险，见 §3.1 方法名白名单）。**T2.2 spike 应把重点从"gem 能不能传 is_ephemeral"转向"服务端是否接受该参数"**（后者只能真机验证）。
