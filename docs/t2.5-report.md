## 2. 归属判断：`bot/migration.rb` 而非 `db/migration.rb`

计划 §2 目录树两处都写了 `bot/migration.rb`（架构图与目录结构），§8 T2.5 只写 `migration.rb`。取 `bot/` 的三条理由：

1. **它的输入是 Telegram 的 Message 语义**（`migrate_to_chat_id` / `migrate_from_chat_id`），是 bot 层协议知识；DB 层（`db/*.rb`）不认 Telegram 类型，`db/settings.rb` 的纪律是「DB 层不碰引擎、不知 bot 协议」。
2. **它由 Router 消费**，与 `bot/handlers/dice.rb` 同层；放 `db/` 会让 `bot/` 反向依赖 `db/` 之外的命名空间约定。
3. 计划的两处目录树都落在 `bot/migration.rb`，与既有实现一致。

内部仍然**只做 SQL**，经注入的 `TenguDB::Connection` 执行——分层靠依赖方向而非目录位置。

## 3. 关键决策

### D1 — 方向归一：`handle(chat_id:, migrate_to:, migrate_from:)` 一个入口

Telegram 升级会向**两侧各发一条**消息，字段形态相反：

| 来源 | `chat.id` | 迁移字段 | 归一结果 |
|---|---|---|---|
| 旧群侧 | old | `migrate_to_chat_id = new` | old=chat_id, new=migrate_to |
| 新群侧 | new | `migrate_from_chat_id = old` | old=migrate_from, new=chat_id |
| 防御（两个都有） | — | — | old=migrate_from, new=migrate_to |

归一之后**两侧做的事逐字相同**，于是「任意顺序到达都幂等」不是靠额外逻辑，而是**结构上无法不幂等**——这是 §12 R5「只见到一侧也能工作」的真正实现，而不是三种分支各写一遍再各自判重。

### D2 — 不动 `log_entries`，schema 零变更

`log_entries` **没有 chat_id 列**（§4.1），靠 `log_id REFERENCES session_logs(id)` 关联。父行的 chat_id 一改，归属自动跟着走。测试用 `PRAGMA table_info(log_entries)` 反证「确实没有该列」，避免后人「顺手补个 chat_id」把外键语义改坏。

同理 T2.4 把 `chat_settings` / `bank_record` 设计成 `(chat_id, thread_id)` 复合键，正是为了让 re-key 退化成单列 `UPDATE`——本任务零 schema 变更。**迁移期间在新群侧新建的行不会被误改**（`WHERE chat_id = old` 只匹配旧侧）。

### D3 — 表清单写死常量，不反射 `sqlite_master`

反射会让「新增表忘了加进清单」变成**静默漏迁移**（数据随群升级消失，且无任何告警）。写死 `TABLES` 常量，漏加是 review 期可见的 diff。表名插值进 SQL 的安全性前提是它来自 frozen 字面量、不含任何外部输入——与 `db/connection.rb` 的「值一律绑定」纪律不冲突。

### D4 — 冲突时**整体回滚**，不做逐表兜底

若目标 id 侧已存在同键行（`chat_settings` 的 PK `(chat_id, thread_id)`），UPDATE 触发 UNIQUE 冲突 → **异常原样抛出、整笔事务回滚**。宁可「数据仍在旧 id 下 + `chat_id_aliases` 无记录」可排查，也不做「逐表部分迁移」留下半拉子账本（那样玩家看到的是「设置还在但账本没了」，比整体没迁移更难查）。router 侧兜住异常（只 warn + 不杀循环）。

实测（见 §4.2 行为实录）：`bank_record`/`secrets` 这两张**在冲突点之前已执行**的表也一并回滚，`chat_id_aliases` 不留半条记录，连接不残留活动事务，清掉冲突行后可直接重试。

### D5 — `alias_conflict` 只 warn 不改写审计行

同一 old_chat_id 已存在 alias 但指向不同 new id（理论上不该发生）时：**保留首次映射**（审计表不改写），re-key 仍以本次消息为准（最新消息是活的事实），并 `warn`。这条路径无法由 Telegram 正常触发，是纯防御。

### D6 — Router 侧 warn 纪律：只记 class + id，不含正文

迁移失败若裸抛，长轮询循环会死；若静默吞掉，群升级后账本无声消失且**没有任何用户可见症状**（迁移消息本就不该回话）。故 `handle_migration` 的 `rescue` 只打 `e.class`，且用 `ensure` 覆盖「未注入 handler」这一路径。测试用假异常消息（`"secret user text"`）+ 假入站正文断言二者都不出现在日志里。

### D7 — DB 连接只开一次，与 DiceHandler 共用

main.rb 原先靠 `dice.settings`（惰性建 Settings）间接开库。T2.5 需要第二个 DB 消费者，若各开各的 `Connection.instance` 虽同实例（按路径 memo），但依赖写法隐晦。改为显式 `dice_db = Connection.instance`，同时注入 `Settings.new(dice_db)` 与 `Migration.new(connection: dice_db)`——**单连接纪律的可见化**（§3 决9）。

### D8 — 一个实施期踩到的真 bug：`#handle` vs `#call`

Router 的注入协议是 `#call(...)`（与 handlers 一致），初版 Migration 只有 `#handle`，端到端用例直接报 `NoMethodError`——**被 router 的 rescue 兜住变成静默跳过**，若无端到端用例就会带着「接线看着对、实则从不迁移」交付。补 `alias call handle` 后修复。这条也说明「静默兜底 + 无端到端」是危险组合，故保留了真 Migration + 真 Router 串联的 `test_end_to_end_router_drives_real_migration`。

## 4. 行为实录（实测，非推断）

### 4.1 正常路径（测试群 id：-1234567890 → -1009876543210）

```
1st      : moved=true total=6 rows={"chat_settings"=>2, "bank_record"=>1, "custom_tables"=>1,
                                     "secrets"=>1, "session_logs"=>1} alias_new=true dir=to
2nd same : moved=false total=0 alias_new=false
3rd from : moved=false dir=from
alias    : {"old_chat_id"=>-1234567890, "new_chat_id"=>-1009876543210, "migrated_at"=>"2026-10-11 16:14:39"}
leftover : old=0 new=2
no fields-> nil
old==new : moved=false aliases=1
```

`chat_settings` 命中 2 行（群级 0 + 话题 88），其余各 1，共 6 行。第二、三次调用 0 行变更、alias 不新增——**幂等的可观测证据**。

### 4.2 冲突回滚（目标 id 侧已有同 PK 行）

```
raised  : SQLite3::ConstraintException
rollback : old cs=2 new cs=1 bank_old=1 bank_new=0 secrets_old=1 secrets_new=0 logs_new=0
aliases  : 0  tx_active=false
retry ok : moved=true total=5 bank_new=1
```

`new cs=1` 是**预先存在**的那行（冲突源），`bank_new=0 / secrets_new=0 / logs_new=0` 证明事务内先执行的表也全部回滚；清掉冲突行后同一连接可直接重试。

### 4.3 三种时序（§12 R5）

| 时序 | 终态 |
|---|---|
| 先 to 后 from | 五表全挂 new、old 归零、alias 1 行 |
| 先 from 后 to | 同上 |
| 只收一侧（只有 to） | 同上 |
| 只收另一侧（只有 from） | 同上 |
| 同一消息连收 3 次 | 同上（首迁 6 行，其余 0 行） |

四条时序用例**共用同一个终态断言函数** `assert_timing_terminal_state`，等价性由结构保证而非三份复制粘贴的断言。

「幂等」的断言不止看 `moved?=false`，还做 `SELECT * … ORDER BY rowid` 的**全表快照逐字比对**（含 `chat_id_aliases`），杜绝「行数没变但内容被二次改写」这种伪幂等。

### 5.3 测试自身的两个真发现

1. **`PRAGMA table_info(log_entries)`** 用来反证「该表无 chat_id 列」——比读 schema.sql 更硬（schema 改了但库没重建时会暴露）。
2. 空库用例里 `DELETE FROM session_logs` **必须放在 `DELETE FROM log_entries` 之后**，否则 `FOREIGN KEY constraint failed`——这是 T2.4 E10（`foreign_keys=ON` 真在生效）的连带证明。
