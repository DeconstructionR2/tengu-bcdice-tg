## 1. 逐行对照要点（db.js / db_wrapper.js → 本实现）

### 1.1 天狗的数据形状

天狗用 Firestore，两篇文档两张 map：

```
private_db / doc(Discord 频道 id) / field(表名) = {
    dice: { 快捷名: 骰式 }, data: { 出目: 结果文本 },
    permission: [KOOREME, 群主, 建表者, 限定用户…],
    datarange: { isUse, max, min } }
public_db  / doc('99')           / field(表名) = 同上
```

- **一篇文档 = 一个频道的所有表**；表名是 map 的 field 名。
  → SQLite 里天然对应「**一表一行**」，唯一性由 schema 的
  `UNIQUE(scope, chat_id, name)` 承担（schema.sql 已存在，本任务未改 DDL）。
- `db.js` 的 `setData(..., {merge:true})` 是**深合并**写：本项目改为
  「事务内读 spec JSON → 改 → 整体写回」，合并规则显式化（§4.2 要求）。
- `db.js:25` 的 `FieldValue.delete()` 哨兵（删 map 的一个键 / 删整个 field）
  → 本项目改为 JSON 键删除 / 行 DELETE（§4.2「JSON 键删除/行 DELETE」）。
- 公共表的固定 doc id `'99'`（db_wrapper.js:3）→ 本项目 `PUBLIC_CHAT_ID = 0`
  占位（§4.1 已说明：0 占位避免 NULL 使 UNIQUE 失效）。
- `db_wrapper.js:3-4` 的 `PUBLIC_CH_ID='99'` / `PUBLIC_DB` / `PRIVATE_DB`
  → 本项目 `scope` 列 + `chat_id` 复合定位。

### 1.3 查找顺序（逐字保留）

`SearchTableDiceroll.js:13-24` 原文：

```js
async getTableData(tableName) {
    //default -> private -> publicで検索。
    let checkDataTable = this.datatable.dataTable[tableName.toLowerCase()];
    if (!checkDataTable)
        checkDataTable = await DB.db.getUserTable(this.channelID, tableName);
    if (!checkDataTable)
        checkDataTable = await DB.db.getUserTable(null, tableName);
    return checkDataTable;
}
```

本实现逐条对应：

1. **default（代码内置）**：`resolve_table(builtin:)`。内置表来自引擎侧
   `nd_datatable`（天狗 `datatable.dataTable`），故**由调用方注入**
   （Hash 或 callable），db 层保持零引擎依赖（同 `db/settings.rb` 纪律）。
   键按 `tableName.downcase` 取——照抄天狗。
2. **频道私有**：`scope='private' AND chat_id=?`。`chat_id=nil` 时跳过本级
   （天狗 `getUserTable(null, …)` 同款）。
3. **公共**：`scope='public' AND chat_id=0`。

顺序常量：`CustomTables::LOOKUP_ORDER == Resolution::SOURCES == %i[builtin private public]`，
单元测试对**常量本身**与三态命中各断言一次。

## 2. 与天狗的语义差异清单（定案项）

| # | 差异 | 定案 | 依据 |
|---|---|---|---|
| ① | **datarange 不设限** | 天狗 `MAX_SAFE_INTEGER`/`MIN_SAFE_INTEGER` → 本项目 JSON `null` | §4.2 明文定案。⚠️ 注意：`datarange` 列是 `TEXT NOT NULL`，**SQL NULL 层面不可行**，故定案落在 JSON 内的 `null`（`DataRange#unbounded?`）。本表键是用户可见的小整数出目，用 ±2^53 当哨兵毫无意义 |
| ② | **权限 id 类型** | 天狗存 Discord **字符串** id → 本项目存 **int64** | Telegram user_id 是整数，与 `secrets.user_id` / `chat_id` 口径统一；比较侧（`permitted?`/`admin?`）一律 `to_i` 归一，手工灌库的字符串仍能命中（有测试钉） |
| ③ | **建表初始权限三元组** | 天狗 `[KOOREME_USER_ID, guild_owner_id, author_id]` → 本项目默认 `[author_id]` | 本项目没有「bot 所有者」概念；T3.4 要复刻群主占一位时显式传 `permissions:`。**位置语义不变**（前三位 = admin 位） |
| ④ | **同名冲突** | 天狗 Firestore 同 field `set` 是**覆盖** → 本项目先查后写 + UNIQUE 兜底，显式回 `ALREADY_EXISTS` | §4.1 已把 UNIQUE 作为静态资产定下；SQLite 没有 field 覆盖语义 |
| ⑤ | **多步写的事务** | 天狗 Firestore 单次 `set` 原子，但「改名」「发布」是**两次调用**，中途失败会留下两张表 / 公共与私有并存 | 本项目把两步合进 `:immediate` 事务（测试用探针钉住入口） |
| ⑥ | **DB 侧大小写** | 天狗内置查找 `toLowerCase()`、Firestore 字段名精确匹配 → 本项目同款：内置源 downcase、DB 侧精确 | 两处都不是笔误，是原样保留。命令层的 `diceName`/`diceString` 小写化（updateDice/deleteDice 的 `array[2].toLowerCase()`）亦属命令层，归 T3.4 |
| ⑦ | **返回值形状** | 天狗 `{result: bool, message: String}` → 本项目 `MutationResult` 六态（`ok`/`not_found`/`already_exists`/`invalid_argument`/`data_missing`/`error`）+ `changed?` | 天狗文案由 handler 出，db 层只给可判别状态；`data_missing` 单独成态是因为天狗那条路径**回 true 但文案不同** |
| ⑧ | **范围钳倒挂** | 天狗 `updateAddition` **不做** `max>=min` 校验（传入的都来自 data 键，天然有序） → 本项目**拒** | 实现级决策：handler 可能算错，倒挂的钳制会让所有出目判失败却毫无提示；宁可建表时就拒 |
| ⑨ | **公共表数据完整性校验** | 天狗 `ct_command/publishTable.js` 的 `dataVerification`（出目区间 vs 登记数据数，`datarange.isUse` 为真时跳过）**不在 db 层** | 它要解析骰式算式，而骰式语义在引擎侧；T3.4 如需应在 handler 实现 |
| ⑩ | **文本载荷的空串口径** | `update_data` 的空结果文本**放行**（天狗命令层 `if (!array[3])` 在 JS 假值语义下空串也拦；其存层本身无校验），`update_dice` 的空骰式**拒**（骰式是结构值） | db 层不做命令层文本校验（与「`set_permissions` 不内置 deletePermission 前三位限制」同一纪律）；命令层空串规则归 T3.4 |

### 天狗 quirk 忠实保留（含「看起来像 bug 的部分」）

- **删一个本来就没有的出目 = 成功**（`ct_command/deleteData.js:17-18` 的
  `if (!userTable.data[dataIndex]) return {result:true, …}`）→ `DATA_MISSING`，
  `success?` 为真，handler 据此选「入力した番号のデータは存在しません」文案。
- **删不存在的表 / 删不存在的快捷名 = 成功**（Firestore 哨兵语义）→ `OK` +
  `changed?=false`，handler 可区分「真删掉了」与「本来就没有」。
- **权限的「前三位是 admin 位」**：天狗 `updateTableName`/`addPermission`/
  `deletePermission`/`deleteTable`（私有分支）只认 `permission[0..2]`，而
  `updateDice`/`updateData`/`deleteDice`/`deleteData` 看**全体** permission。
  值对象保留该语义（`#admins`/`#admin?`/`#permitted?`），**位置即层级，不做集合化简**。
- **`deletePermission` 不许删前三位**（天狗「管理範囲のチェック」）→ 属命令层，
  db 层的 `set_permissions` 是整体替换，不内置那条限制；T3.4 需自行拦。
- **发布是「移」不是「复制留着」**：`publishTable.js:22-27` 写公共后
  `deleteTable(ids.channelId, …)` 把私有那张删掉——本层同款（单事务内 INSERT…SELECT + DELETE）。

## 3. 实现级决策清单

1. **公共行只能由 `publish_table` 产生**：`create_table` 显式拒 `scope: :public`
   （对齐天狗——`db_wrapper.js:65-70` 的 `_createTable(null, …)` 唯一调用方就是
   `publishTable`）。这样「公共表的写入路径」全库只有一处（发布 + 既有公共行的编辑/删除）。
2. **私有表禁 `chat_id=0`**：0 是公共行的占位，私有表写进去会与公共行抢
   UNIQUE 槽位、且语义上是黑洞（同 `db/bank.rb` 的 `normalize_chat_id` 守卫）。
3. **改名的原子性**：天狗「写新 + 删旧」两调用 → 一条 UPDATE（SQLite 下
   UNIQUE 保证改名不会撞已存在的新名，应用层再先查一次只为给出可读状态）。
4. **发布的原子性**：`INSERT … SELECT` 复制整行 + `DELETE` 私有，同事务；
   UNIQUE 异常 → 回滚并回 `ALREADY_EXISTS`（私有表原样不动）。
5. **`MutationResult` 六态 + `changed?` 双轴**：状态给文案、`changed?` 给
   「真删掉了 vs 本来就没有」。六个状态谓词互斥（有测试钉）。
6. **读改写统一骨架 `edit_row`**：spec / permissions / datarange 三列的改动
   全部走同一个事务模板，杜绝「新加一列忘了包事务」。
7. **事务块内绝不 return**（同 `db/bank.rb`）：块内只赋值 `outcome`。
8. **JSON 列容错**：坏 spec → 空表、坏 permissions → 空数组、坏 datarange →
   不设限，只 warn（**只有结构性描述，无用户正文**）。spec **只解析一次**
   （解析两次会让 warn 重复两条——测试钉住了 warn 计数）。
9. **SQL 插值面**：只有本文件 frozen 常量 `TABLE` / `COLUMNS` / `SCOPE_*` /
   `PUBLIC_CHAT_ID` / `DEFAULT_DICE` / `LOOKUP_ORDER`；表名/骰式/条目文本
   一律绑定（有 SQL 元字符注入面测试）。
10. **`DELETE` 判定删没删到读 `Connection#changes`**（execute 返回结果集）。

## 6. 遗留风险与下一步

   - `publish` 前的 `dataVerification`（出目区间 vs 数据数，差异 #⑨）；
   - 权限文案与 admin 位校验（含「不许删前三位」；注意母本 `deleteTable` 的
     **public 分支只认 `permission[0]`**、私有分支才认前三位——handler 按 scope 区分）；
   - 天狗「建表/发布时新名不得撞**内置表**」的检查（createTable.js:10-11、publishTable.js:13-14；
     ⚠️ 母本**改名不查内置表**——updateTableName.js 无 datatable 引用，若要补属超越母本，需注明）；
   - 建表撞名检查要覆盖 **内置表** 与私有表两路（母本 createTable.js:10-13 先查内置再查私有）。
   - `dataIndex`（条目出目键）的命令层校验 `/^\d+$/`（母本 deleteData.js 同款；
     本层 normalize_data_index 放行非数字键——db 层不管文本合法性，归 handler，
     kimi T3.3 评审提案 #7 登记）；
2. **datarange 的实际生效（钳制判定）在本层之外**：本层只存 `isUse/max/min`，
   真正的「出目超出钳制范围则报错」是掷骰时的事（T3.4 handler 或引擎桥）。
