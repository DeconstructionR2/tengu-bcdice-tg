## 3. 关键决策

### D1 — T2.4 遗留的 aux_enabled：**先查列存在，再 ALTER**

`CREATE TABLE IF NOT EXISTS` 在表已存在时**整条跳过**（连同其中的新列）。故「在 schema.sql 里加一列」只对**新库**生效，部署前建好的库会永远缺列，直到某条 SQL 碰到它才报 `no such column`——而那一刻已经在生产。

**两条腿的范式（此后加列一律同此）**：

1. `db/schema.sql` 改表结构 → 新库一次建全；
2. `db/connection.rb` 的 `COLUMN_ADDITIONS` 登记同一条 ADD COLUMN → 首连时 `ensure_column` 对旧库补列。

`ensure_column` 的顺序是「先探表在不在，再探列在不在」：表不存在直接返回 false（不去 ALTER 一个不存在的表，那会炸成 `no such table` 并掩盖真实问题）；列已存在返回 false（**幂等性的来源**，因为 SQLite 的 ALTER TABLE 至今没有 `IF NOT EXISTS`）。

`apply_column_additions` 单条失败**不让连接建立失败**：数据库能被打开、其余表可用，比启动即崩掉更有用（缺列是可用性问题，且被记进日志可被看见），且 warn 只打 `e.class`。

**测试把纪律钉死**（3 条反射守卫，任一腿漏了当场红）：
- 凡登记的 (表,列) 必须**由 schema.sql 直接建出**（防止「新库也靠 ALTER 补」的两份抄本漂移）；
- 登记的 `DEFAULT` 必须与 schema.sql 建出的列默认值**逐字一致**（否则新群在新库默认开、旧库默认关）；
- `NOT NULL` 的登记列必须带 `DEFAULT`（否则在有数据的旧库上 ALTER 直接失败）；
- 另加一条：登记项的表名/列名/定义不得含引号分号（它们会被插值进 SQL，是常量不是输入——与 `Migration::TABLES` 同一纪律）。

### D2 — aux_enabled 是**每群一份**，不是每话题一份

计划 §6 的口径是「每群 `/settings` 可关辅助轨」。故读写都固定 `thread_id=0`，话题内执行也写群级行，话题行的值一律不读。

这与 `game_system` 的三级查找**刻意不同**：规则系统是「话题可以有自己的」，辅助轨开关是「这个群烦不烦抢话」——让每个话题各关各的只会制造「A 话题以为关了、B 话题还在抢」的错觉。

代价：用户在话题里关掉，General 话题也一起关。文案与测试都写明了这一点（回复带「（全群生效）」、`test_aux_switch_applies_to_all_topics_of_the_chat`）。

### D3 — 权限判定与开关查询**都 fail-closed**，但方向不同

| 层 | 失败时 | 为什么 |
|---|---|---|
| `Admin#admin?` | **false** | 误判成「是管理员」= 任何群成员能改别人的群设置 / 改别人的 CT；误判成「不是」最坏只是「管理员自己再试一次」。 |
| `Router#aux_track_enabled?` | **false**（T2.3 既有） | 已在用户关掉辅助轨的群里继续抢话 = 防抢话纪律破防。 |
| `SettingsHandler#authorized?` | **false** | 同 admin?；且 `admin?` 若仍抛异常也当拒绝（双重保险，不能让判定层异常变成放行）。 |

**`SettingsHandler` 未注入 `admin` 时群内一律拒绝**（不是「不校验 = 放行」）。这是本任务实施期的一次自我修正：初版留了「未注入 = 免检」的宽松模式以便单测，但那等于「忘了注入 admin → 所有人都能改群设置」——最坏的一种故障，且完全静默。改为 fail-closed 后，所有单测改注入假 admin（`FakeAdmin`），顺带多钉了两条用例。

### D4 — Admin 的缓存**只缓存 true**

管理身份是**可变的**（被撤职/被提升）。缓存一个 false 会让刚上任的管理员在 TTL 内用不了 `/settings`（用户看到的是「明明是管理员却被拒」）；缓存一个 true 则让刚被撤职的人在 TTL 内**仍可改设置**（命中期间零 API 调用，是「窗口内不限次数」，窗口最长 5 分钟——kimi T2.6 评审更正：此前误写为「多改一次」），TTL 到期即恢复。两者代价不对称，故只缓存已确认的 true。TTL 取 300s（对每群 20 条/分的低频 bot 够用）。时钟可注入 → TTL 用例零真实等待。

### D5 — getChatMember 双通道：gem 为主、raw_api_call 兜底

gem 2.8.1 的 `Api::ENDPOINTS` 已收录 `getChatMember`（endpoints.rb:71 → `Types::ChatMember`），故主通道走 `@api.api_client.api.get_chat_member`；gem 未收录/失败时兜底走 `raw_api_call`（计划 §12 R2 的保底通道，与 `bot/telegram_api.rb` 里其它端点同一纪律）。两条通道的返回都被 `status_of` 归一成 String status（gem 返回 dry-struct，raw 返回 Hash）。

**实施期实测修掉的一个真 bug**：初版在 `from_gem` 里 `rescue StandardError; raise`，让 gem 的异常冒到 `fetch_status` 的统一 rescue，于是「gem 报错 → raw 兜底」这条路**根本走不到**——白丢一条保底通道，且网络错时 raw 也大概率一起错，等于凭空少了一层。改为 `from_gem` 就地收口成 nil（记一笔 warn），`from_raw` 仍会被尝试。探针实测（改前 19/24 → 改后 24/24）。

### D6 — 匿名管理员：本类**不读 message**，只吃 (chat_id, user_id)

§0.2.4 实证：匿名管理员的消息 sender 是 `GroupAnonymousBot`（user id = 1087968824），**不是真人 id**；但 `callback_query.from` 仍是真人。故：
- 用 `message.from.id` 去查，查到的是「匿名 bot 是不是管理员」，**永远返回 false** → 匿名管理员被误拒；
- 职责分离让这个坑在 **handler 侧**解决：把 `callback_query.from`（按钮回调）或 `/settings` 的 user_id 传进来。T3.1 的暗骰「公开」按钮走 `callback_query.from`，正是天然正确的来源。

本类保留 `ANONYMOUS_ADMIN_USER_ID` 与 `anonymous_admin?`：若入参就是匿名 bot id，说明调用方取错了来源，**在打 API 之前**就 fail-closed 返回 false（并省掉一次无用请求）。`anonymous_admin?` 刻意**不经** `normalize_user_id`（那个方法把匿名 bot id 当无效值滤掉了，用它判会永远 false——实施期探针实测踩到）。

### D7 — 私聊豁免：恒 true 且**零 API 调用**

私聊没有「群管理员」这回事，且 getChatMember 对私聊也不该用来判权限。故 `admin?` **先判 chat_type**：显式 `"private"` → 恒 true 且一次网络都不打。`chat_type` 为 nil 时**按群处理**（打 API 查询）——「没传 type」不等于「私聊豁免」，未知必须按更严的一侧。

### D8 — `/settings` 非管理员拒答**用一句**，不静默

这与辅助轨的「静默防抢话」**刻意相反**：辅助轨是 bot 自己猜这行是不是骰式，回话就是抢话；slash 主轨是用户点名问了（打了 `/settings aux off`），静默只会让用户以为 bot 挂了或命令拼错了。

**只读总览（无参）不做权限门**：普通成员也该能看到本群设置——否则群里没人知道该怎么改。总览不触发 getChatMember（有断言）。

### D9 — 子命令只认 `on`/`off`，其余走用法提示

不猜方向：`enable`/`disable`/`开启`/`开` 一律回用法。猜错的代价是「静默关掉/打开了群设置」，而用户本来只想看看设置长什么样。纯 ASCII 定案（§13 第 2 项），大小写不敏感（`AUX ON` 也认）。

### D10 — `fetch_row` / `entries_for_chat` 的 SELECT 加了 aux 列

这两个方法本就标注「/settings 展示与测试断言用」，让 `/settings` 直接复用它们而不是新写一个查询——避免同一个事实有两个取数路径。`entries_for_chat` 的返回 Hash 多了 `"aux_enabled"` 键（既有测试不受影响：它们只断言行数与 `game_system`）。

### 5.3 测试自身的三个真发现

1. **`PRAGMA table_info` 不接受绑定参数** → `column_names` 走 `pragma_table_info(?)` **表值函数**（能绑定），表名无需拼进 SQL 字符串（与「值一律绑定」纪律同源）。
2. **`:memory:` 库经历不了「首连补列」的语义**（每次新建都按新 schema 建全）→ 补列用例全部用真文件库（tmpdir 自清理）。
3. **父进程从不 require gem**（那会引入副作用）→ main 冒烟的 update 列表必须写成**子进程里的源码文本**，不能在父进程构造 `Telegram::Bot::Types::*` 对象（实测 `NameError: uninitialized constant TestMainStartup::Telegram`）。
